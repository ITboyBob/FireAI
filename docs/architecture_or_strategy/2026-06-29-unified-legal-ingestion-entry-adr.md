# ADR-1：统一法规摄取入口与策略路由

**状态：** 已接受
**日期：** 2026-06-29
**角色：** `architecture_or_strategy`
**Linear 记录：** `BOB-8`

## 1. 决策摘要

保留 `scripts/import_new_corpus.py` 作为唯一、轻量的法规摄取 CLI，由其委托统一摄取编排器。提取策略按 W/PT/PS 注册，正文边界策略按 S1/S2/S3/S4 注册，禁止为 W-S1、W-S2、PT-S1 等分类组合新增 CLI 或组合策略。

所有正式提交必须先取得质量资格，再复用现有 staging、两次 preflight、索引追加、回滚和 manifest 最后写入。现有 `run_incremental_import()` 必须委托统一编排器，或在调用方迁移后删除。

## 2. 背景

当前 `scripts/import_new_corpus.py` 允许单个 DOC/DOCX 文件通过 `run_incremental_import()` 直接进入 `normalize → parse → chunks → commit`。

W-S1 里程碑提出新建 `import_ws1_corpus.py` 时，暴露了两个长期问题：

1. 若每种提取类型与正文结构组合都新增入口，入口数量会随 W/PT/PS 与 S1—S4 的组合膨胀。
2. 若旧入口继续直通提交，新入口的质量门禁无法成为系统级强制规则。

问题不在于脚本文件数量本身，而在于用户契约、编排逻辑和提交资格出现分叉。

## 3. 决策

### 3.1 唯一薄 CLI

`scripts/import_new_corpus.py` 是唯一用户入口。它只负责：

- 解析互斥输入；
- 加载运行配置；
- 调用统一摄取编排器；
- 输出稳定的中文结果、错误码和退出码。

CLI 不实现格式判断、正文边界、质量门禁或提交事务。

### 3.2 输入互斥

单文件输入与显式批次输入必须使用互斥参数。现有位置参数和 `--source` 语法继续兼容单文件场景，但不得同时使用或传入多个来源。

显式批次引用冻结清单，逐文件处理并串行执行正式提交，不建立多文件全局事务。

### 3.3 双轴独立策略

- 提取轴注册 W、PT、PS 策略；
- 正文边界轴注册 S1、S2、S3、S4 策略；
- PX 是异常或混合探测结果，不是自动提交策略；
- 不注册 W-S1、W-S2、PT-S1 等组合策略。

编排器分别选择两类策略并组合运行，使新增 PT 时可以复用 S1，新增 S2 时可以复用 W。

### 3.4 稳定结果语义

- `unsupported`：系统尚未实现完成本次处理所需的能力；
- `review_required`：已有候选证据，但分类、边界或质量仍有歧义；
- `failed`：执行、质量契约或提交过程发生明确失败。

三种结果必须使用稳定错误码和可区分的退出码，并且都保持零正式写入。

### 3.5 质量资格与提交

统一编排器只有在全部必需门禁通过，或人工复核后重新执行机械门禁并通过时，才签发质量资格。

提交层继续复用现有 Append-Only 能力：

- staging 隔离；
- 提交前两次 preflight；
- 关键词与向量索引追加；
- 正式发布回滚；
- manifest 最后写入。

提交层不得自行降低或绕过质量资格。

### 3.6 服务层不得保留旁路

`run_incremental_import()` 必须改为委托统一编排器，或在所有调用方迁移后删除。即使只用于测试，也不得保留旧的 `normalize → parse → chunks → commit` 直通实现。

## 4. 被否决的方案

### 4.1 每种分类组合一个 CLI

示例包括 `import_ws1_corpus.py`、`import_ws2_corpus.py`、`import_pts1_corpus.py`。

否决原因：

- 入口数量随分类组合增长；
- 公共门禁和提交逻辑容易复制、漂移；
- 用户需要理解内部分类才能选择命令；
- 每个组合都要重复 CLI、错误处理和回归测试。

### 4.2 长期保留新旧双入口

新入口执行质量门禁，旧入口继续兼容原始直通行为。

否决原因：

- 形成可绕过质量门禁的旁路；
- 两个入口对同一文件可能给出不同结果；
- “兼容”会把不安全行为固化为长期契约；
- 测试无法证明所有正式提交都经过统一资格。

### 4.3 把全部策略写进旧脚本

保留单一脚本，但让脚本直接承担分类、提取、边界、质量和提交。

否决原因：

- 表面上入口紧凑，内部仍是高耦合单体；
- 策略不能独立测试和复用；
- CLI 参数与业务状态难以保持稳定；
- 后续 PDF/OCR 能力会继续扩大脚本职责。

## 5. 兼容性后果

### 5.1 保留的兼容性

- `scripts/import_new_corpus.py` 路径不变；
- 单文件位置参数继续可用；
- `--source` 继续可用；
- 现有 Append-Only 正式提交机制继续复用；
- 成功结果仍可报告 run、document、chunk 和 manifest。

### 5.2 有意收紧的行为

- DOC/DOCX 不再因可转换且 chunk 非空就直接获得提交资格；
- 未支持类型返回 `unsupported`，不再用“只支持 DOC/DOCX”概括所有结果；
- 边界或质量有歧义时返回 `review_required`，不得猜测后提交；
- 处理或提交失败返回 `failed`，并明确失败阶段；
- 旧服务函数不能绕过统一编排器。

这属于“语法兼容、行为收紧”。安全边界优先于维持旧直通结果。

## 6. 对计划和测试的约束

- 未来按新增能力编写计划，例如 PT 提取策略或 S2 正文边界策略；
- 策略组合只增加集成验收，不复制整套入口和执行计划；
- W-S1 是首个实现组合，不是独立架构入口；
- 必须测试旧命令语法经过统一编排器；
- 必须测试 `unsupported`、`review_required`、`failed` 均为零正式写入；
- 必须测试服务层没有可绕过质量资格的提交路径；
- 批次测试必须验证逐文件失败隔离和共享索引串行提交。

## 7. 权威关系

[法规摄取总体架构](./2026-06-29-legal-ingestion-overall-architecture.md)负责展开本决策在全系统中的组件和数据流。

四篇多格式专项设计分别负责分类与提取、正文边界与中间格式、质量门禁与批次状态，以及 `todo` 多格式处理范围。它们不得重新引入组合 CLI、组合策略或旧提交旁路。

[法规摄取能力路线图](../project_or_workflow/2026-06-29-legal-ingestion-capability-roadmap.md)负责记录策略状态和实施顺序；里程碑执行计划负责具体代码、TDD 和验收步骤。两者都不得改变本 ADR，除非先以新的 ADR 明确替代。

## 8. 重新评估条件

只有出现以下情况之一，才需要以新 ADR 重新评估本决策：

- 法规摄取出现本地 CLI 之外的正式用户入口；
- Append-Only 提交事务被新的正式存储模型替代；
- 提取轴或正文边界轴被证明确实不能独立组合；
- 批次业务需要法律上不可拆分的全局事务。

在新 ADR 被接受前，本决策持续有效。
