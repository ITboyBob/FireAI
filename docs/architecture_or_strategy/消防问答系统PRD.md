# 消防问答系统PRD

## 文档权威性

- 本文是本仓库当前唯一产品标准，回答“产品为什么做、面向谁、做哪些能力、不做哪些能力、怎样才算产品验收通过”。
- 技术标准、仓库结构、运行命令、工程约束和具体实现边界统一放在 [工程技术标准](./工程技术标准.md)；本文不承担技术手册职责。
- [一期 RAG 设计文档](../reference_material/2026-03-28-fire-law-rag-design.md) 仅作为历史设计背景保留。若它与本文存在冲突，产品口径一律以本文为准；若它与工程技术标准存在技术口径冲突，一律以工程技术标准为准。

## 产品定位与能力基线

产品定位：面向消防部门工作人员，围绕消防法律法规与技术规范提供法规制度查询、消防检查指引、技术规范判定、执法程序查询及具体案情执法判断，作为消防业务中的知识与决策辅助工具，输出仅供工作人员业务参考，不替代法定执法程序及具有法定权限人员作出的正式行政决定

产品基线：

- 用户可以围绕消防法规直接发起问题，并在同一会话中继续追问。
- 系统回答必须基于已建好的法规检索证据，而不是绕过检索直接让大模型自由发挥。
- 回答结果必须让用户能看到结论、法律依据、条款原文和必要的修正提示。
- 当证据不足时，系统必须提示“无法作出可靠判断”，并提示用户“补充信息”
- 用户进入历史会话或刷新对话页时，原有会话不会丢失。
## 产品边界和红线

产品边界：
- 使用对象边界：系统仅面向经授权的消防部门工作人员使用，不作为面向社会公众、企业或其他主体的法律咨询服务。
- 业务场景边界：系统仅处理法规制度查询、消防检查指引、技术规范判定、执法程序查询及具体案情执法判断五类消防法律业务场景。
- 知识范围边界：系统仅基于纳入知识库的消防法律法规、规章、规范性文件、技术标准规范及相关业务材料回答。
- 判断能力边界：系统仅依据用户输入的提示词和能检索到的法律规范回答用户问题
- 法律效力边界：系统输出可以包含明确的参考结论及其依据，但始终属于业务辅助意见，不具有行政决定、行政执法文书或其他正式法律行为的效力。

产品红线：
- 不得伪造或无依据生成法律结论：所有回答必须能够回溯至实际检索到且与问题相匹配的有效规范来源
- 知识库之外的问题禁止回答

## 解决方案

本期将当前系统前端正式收敛为**两个产品页面态 + 一条明确的发问跳转链路**：

1. `首页态`
   - 负责启动问答，不承载历史消息流。
   - 采用深色 command center 方向：左侧为品牌和最近会话，右侧为英雄区、输入框和能力卡片。
   - 首屏必须让用户清楚知道“现在可以直接输入问题”。

2. `对话态`
   - 负责展示当前会话的消息流、修正提示、法律依据和证据区。
   - 采用浅色 evidence desk 方向：左侧仍保留会话导航，右侧重点展示提问、回答、法律依据和证据卡片。

3. `首页 -> 对话页` 跳转链路
   - 用户在首页输入并发送问题后，系统必须先创建或确定当前会话，再显式切换到对话态。
   - 首页首问仍先调用 `POST /api/conversations` 创建会话，再调用 `POST /api/conversations/{conversation_id}/messages/stream` 发送问题。
   - 发送后必须立即渲染用户消息和状态占位，并通过后端 NDJSON 状态事件更新提示文字。
   - 当 `completed` 事件返回可信 `assistant` payload 后，再由前端按“回答正文 -> 法律依据列表 -> 条文原文证据”的顺序逐字呈现。

4. `继续追问` 链路
   - 用户进入对话态后，`Enter` 发送、`Shift+Enter` 换行。
   - 每次提问都重新检索最新证据，但前端必须让用户感知到“我仍在同一会话中继续追问”。

5. `产品真实能力约束`
   - 本期采用后端 NDJSON 状态流，不采用 `SSE` 或 `WebSocket`。
   - 本期不是模型 token 原生流，不展示未校验草稿，不做未校验 `delta`。
   - 后端不持久化 `partial message` 或 `delta`，不新增 `delta` 表。
   - 本期没有附件上传。
   - 本期没有多标签页实时同步。
   - 因此前端不得用可点击入口、假图标或假交互暗示这些能力已经可用。

本期的目标不是像素级复刻参考图，而是把参考图背后的**结构、层次、状态跃迁和交互纪律**落成可以执行和测试的产品约束。


## 产品决策

### 一、技术边界

- 当前采用后端 NDJSON 状态流，但不是模型 token 原生流；前端只能在 `completed` 后基于可信 payload 做客户端逐字呈现。

### 二、信息架构与页面模型

- 前端必须显式区分两个页面态：
  - `首页态`：负责发起问题。
  - `对话态`：负责展示当前会话。
- 产品行为上必须至少支持两个 URL：
  - `/` 对应首页态。
  - `/conversations/{conversation_id}` 对应对话态。
- 即使短期仍然复用同一套 HTML 模板或同一份静态资源，**产品契约上也必须表现为两个明确页面**，不能继续把“有没有 activeConversationId”当作全部页面模型。
- 首页发送首条问题时，系统必须先建立会话，再进入 `/conversations/{conversation_id}`。
- 点击历史会话时，系统必须进入对应 `/conversations/{conversation_id}`，并恢复该会话详情。
- 删除当前打开的会话后，系统必须离开失效会话 URL，回到 `/` 或其他有效会话 URL。

- 首页视觉方向为深色、集中、带“command center”气质，但不得直接照抄英文文案。
- 首页主区域必须包含：
  - 视觉标题区
  - 主输入框
  - 发送入口
  - 预设问题卡片
  - 最近会话/最近调查入口
- 首页主区域不得展示历史消息流、法律依据列表或证据卡片，这些属于对话态职责。
- `Starter Cards` 是首页一级组件，不得挂靠在线程空状态的附属渲染里。
- 点击预设问题卡片的默认行为为：填充输入框并聚焦输入，而不是静默触发请求。
- 当系统没有任何历史会话时，首页仍然完整成立；“空列表”只能影响左侧列表，不得破坏首页主体。

- 对话态视觉方向为浅色、留白更多、重点突出证据和结构化信息。
- 对话态必须包含：
  - 当前问题消息
  - 助手回答区
  - 修正提示区（在需要时显示）
  - 法律依据区
  - 证据区
  - 底部持续可用的输入区
- 证据区应以卡片或块级证据模块展示，不得退化为普通无层次长文本。
- 修正提示必须是独立提示块，不得只用一句颜色很淡的辅助文案草草带过。
- 对话态允许出现空会话，但空会话占位不得复用首页 Hero 和 Starter Cards，以免再次混淆首页态与对话态。

### 三、交互行为契约

- `Enter` 发送消息。
- `Shift+Enter` 换行。
- 当事件处于输入法组合态时，不得因为 `Enter` 而发送消息；必须等待组合态结束。
- 空白消息不得提交。
- 提交进行中时，发送按钮和重复键盘发送应被抑制，避免同一输入被连发。
- 若请求失败，输入框中的原始用户输入不应被无条件丢弃；用户应能看到失败并继续编辑或重试。

- 产品必须继续支持会话创建、读取、重命名、删除和发送消息这些用户动作。
- 首页发送首条问题时，用户感知上必须是一个连续动作：提交问题、进入对话页、看到自己的问题和处理中占位。
- 仅打开历史会话时，只能恢复既有详情，不得产生新的回答、轮次或模型调用。
- 首页态与对话态必须在页面行为上清晰区分；检索、回答生成和证据组织必须作为系统能力稳定产出，而不是依赖用户在界面上手工拼接。

### 四、系统接口协议

- 统一命名为：**后端 NDJSON 状态流，最终可信结果由前端逐字呈现**。
- 新增消息发送接口为 `POST /api/conversations/{conversation_id}/messages/stream`。
- 请求体复用 `UserMessageInput`，字段为 `message`。
- 响应头为 `Content-Type: application/x-ndjson; charset=utf-8`。
- 每行是一个完整 JSON 事件；正文换行必须由 JSON 转义；前端解析必须使用 buffer，不能假设一次 `read()` 就是一行。
- 事件类型固定为 `received`、`retrieving`、`generating`、`organizing_evidence`、`completed`、`error`。
- `received` 只表示后端已接受请求且已成功持久化用户消息，必须携带 `persisted: true`。
- 状态事件只更新提示文字，不生成回答正文。
- `completed.assistant` 等价现有 `SendConversationMessageResponse.assistant`，字段固定为 `message_id`、`answer`、`legal_basis`、`clause_texts`、`correction_notice`、`created_at`。
- 后端必须在发送 `completed` 前完成模型完整 JSON、schema 校验、引文校验、presenter 证据筛选、assistant message / turn / snapshot / history summary 落库。
- 前端收到 `completed` 后，按 `answer -> legal_basis -> clause_texts.path/text` 的顺序做客户端逐字呈现。
- 逐字呈现期间不得立即 `loadConversationDetail` 覆盖本地状态；完成后可刷新会话列表，必要时延后刷新详情。
- 一次性 `POST /api/conversations/{conversation_id}/messages` 保留兼容。
- 流开始前可返回 HTTP `404 / 503 / 422`；流开始后用 `error` 事件表达失败。
- 流开始后的 `error.code` 至少包括 `model_error`、`internal_error`；`persistence_error` 为保留扩展码，仅当 `received` 已发出后的持久化步骤失败时使用。前端以 `message` 文案向用户呈现失败类型，`code` 用于日志与后续增强。
- 失败后可能已经落库用户消息；第一版不做幂等重试，错误后应保留输入内容，并提示重试可能产生新的用户消息。

*注：本节字段级协议细节未来应下沉至《工程技术标准》，PRD 仅保留产品行为口径。*

### 五、视觉与文案

- 首页和对话页必须采用不同但同属一套品牌体系的视觉层次：
  - 首页更像启动台。
  - 对话页更像证据审阅台。
- 主文案默认使用中文；英文可作为辅助标签或品牌装饰，不得承担主要操作说明。
- 左侧会话导航在两个页面态中都应稳定存在，形成统一产品骨架。
- “最近调查 / 最近会话”必须来自真实会话数据，不得用静态占位长期冒充。
- 如果某个视觉元素当前没有真实能力支撑，就不应被渲染成一个看起来能点击的正式控件。

## 测试决策

- 产品验收只关心外部行为，不绑定内部实现细节。前端验收重点是“用户是否真的完成了页面跳转、输入、等待和恢复”，而不是“内部调用了哪个 DOM 辅助函数”。
- 本期前端重构至少需要覆盖以下行为：
  - 首页态是否渲染首页骨架而不是旧的历史管理首屏。
  - `Starter Cards` 是否在首次进入首页时稳定可见。
  - 点击预设问题卡片后是否正确填充输入框。
  - `Enter` 是否发送、`Shift+Enter` 是否换行、输入法组合态下 `Enter` 是否不会误发。
  - 首页发送首条问题后是否进入对话态，并显示用户消息与处理中占位。
  - 对话态加载历史会话时是否只读取详情而不触发新模型调用。
  - 删除当前会话后是否正确离开失效会话页面。
  - 刷新对话页后是否仍能恢复到同一会话。
  - NDJSON 状态事件是否按协议更新提示文字，且不生成正文。
  - `completed` 后是否按 `answer -> legal_basis -> clause_texts.path/text` 顺序逐字呈现。
  - typewriter 期间是否不会立即 `loadConversationDetail` 覆盖本地状态。
  - 流式错误后是否保留输入、提示重试风险并抑制重复提交。
- 本期还必须覆盖 RAG 产品底线：
  - 有证据时，回答必须展示可核对的法律依据和条款原文。
  - 证据不足时，必须明确拒答或提示不足。
  - 索引缺失时，必须提示建库未完成。
  - 追问导致依据变化时，必须展示修正提示并切换到最新证据。
- RAG 质量信号（如拒答准确性、依据可核对率）的量化指标与测量方法由评测体系定义，见 [新评测系统设计总卷](../../新评测系统设计总卷.md)；本期产品验收只要求行为底线达标。
- 本期流式状态专项还必须覆盖：
  - 服务层事件顺序与共享回答链路。
  - API 层 `TestClient.stream` 的 NDJSON 解析、响应头和错误事件。
  - 前端 buffer 解析、typewriter、错误态和重复提交抑制。
  - 现有验证使用 fake chat client 配合 `tmp_path` 假索引，未依赖真实 `data/index/`。

## 非本期范围

- `WebSocket`、`SSE`、模型 token 原生流、未校验草稿流、未校验 `delta`、`partial message/delta` 持久化和新增 `delta` 表。
- 在线附件上传、图片上传、拖拽上传及其 OCR 工作流；离线摄取链路的 OCR 提取策略不受此限，见 [法规摄取总体架构](./2026-06-29-legal-ingestion-overall-architecture.md)。
- 多用户账号、权限体系、共享会话和协作编辑。
- 会话搜索、标签、收藏、导出和批量管理。
- 多标签页实时同步和跨设备同步。
- 真正的前端 SPA 框架迁移；本期不把“换框架”当作默认解法。
- 参考图的像素级复刻；本期追求的是结构、层次和体验对齐，不是视觉一比一还原。
- 自动法律裁判、高风险法律建议、法律责任结论替代。
- 知识图谱、三元组联动、微调、重排训练和多 Agent 自动规划。

## 补充说明
- 有状态流，不等于可以展示未校验模型草稿。
- 前端逐字呈现，不等于后端提供模型 token 原生流。
