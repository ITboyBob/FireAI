# 法律文件双轴分类与提取器路由专项设计

**状态：** 已批准方向的专项设计  
**适用范围：** `法律文本/todo/` 中待处理法律文件的格式探测、分类和文本提取  
**不适用范围：** 正文边界识别细则、统一中间格式最终定义、质量门禁、批次状态、代码实施步骤  
**依赖结论：** 本设计阶段无需新增依赖，沿用现有 conda 环境 `fire`；PDF 与 OCR 依赖仅定义能力边界，不在本文选型或安装
**上位设计：** [法规摄取总体架构](./2026-06-29-legal-ingestion-overall-architecture.md)

## 1. 目标

本设计解决现有增量导入机制只能按扩展名接收 DOC/DOCX、无法区分文本型 PDF 与扫描型 PDF、也无法证明提取结果可信的问题。

路由层必须在进入正文边界识别和法律结构解析前完成三件事：

1. 根据文件真实格式选择提取器，而不是信任扩展名。
2. 根据提取证据判断结果属于可继续处理、需要人工复核或确定失败。
3. 为后续正文边界识别保留必要的页级和行级证据，同时禁止附件、评分表和文书模板进入正式语料。

## 2. 设计边界

### 2.1 本文负责

- W、PT、PS、PX 四类提取分类及其判定顺序。
- S1—S4 内容结构分类在路由阶段的用途。
- Word、文本型 PDF、扫描型 PDF 提取器的共同输入输出契约。
- 现有 `resolve_explicit_sources`、`textutil`、`clean_text` 的复用边界。
- 提取失败和证据不充分时的人工复核条件。
- PDF 与 OCR 能力的依赖边界。

### 2.2 本文不负责

- 目标法规标题、第一条、最后一条和附件边界的具体识别规则。
- 正式统一中间格式的字段定义和持久化规则。
- 条号连续性、重复条文、污染文本等提交前质量门禁。
- 批次任务状态机、失败恢复和 append-only 提交过程。
- 包选择、安装命令、代码任务和测试实施步骤。

### 2.3 与其他设计文档的权威关系

- [法规摄取总体架构](./2026-06-29-legal-ingestion-overall-architecture.md)：负责唯一入口、统一编排、独立策略注册、结果语义和跨组件边界。
- [统一法规摄取入口 ADR](./2026-06-29-unified-legal-ingestion-entry-adr.md)：负责记录禁止组合 CLI、组合策略和旧提交旁路的决策。
- [多格式法律语料摄取专项总设计](./2026-06-28-multi-format-legal-corpus-ingestion-design.md)：负责 `todo` 多格式处理范围、组件关系和数据流。
- [法律正文边界与统一中间格式专项设计](./2026-06-28-legal-content-boundary-and-intermediate-model-design.md)：负责正文保留范围、排除内容和正式中间格式。
- [法律语料质量门禁与批次状态专项设计](./2026-06-28-legal-ingestion-quality-gates-and-batch-state-design.md)：负责质量门禁、人工复核状态、批次报告和提交条件。
- [todo 法律文件评估基线](../reference_material/2026-06-28-todo-legal-corpus-assessment.md)：记录当前真实文件的分类证据和实测问题，不制定长期规则。

分类与提取规则以本文为准，其他文档不得复制并形成第二套规则；本文不得把 W/PT/PS 与 S1—S4 固化为 W-S1 等组合策略。

## 3. 双轴分类模型

每个来源文件同时拥有一个提取分类和一个内容结构分类：

```text
文件真实格式与可提取性 → W / PT / PS / PX
提取后内容组织形式     → S1 / S2 / S3 / S4
```

第一轴决定“由谁提取”；第二轴决定“提取结果以何种风险等级交给正文边界识别”。两者不能合并为一个分类，也不能只按扩展名分类。

## 4. 第一轴：提取分类

### 4.1 W：Word 文件

**判定特征：**

- 真实文件签名为 OLE 复合文档，并且内容可由 Word 转换链路读取；通常对应 `.doc`。
- 或真实文件为 ZIP 容器，且包含 `[Content_Types].xml`、`word/document.xml` 等 WordprocessingML 核心项；通常对应 `.docx`。
- `textutil` 转换成功，输出非空，并达到最低可用文本量。

**典型特点：**

- 大多数文字可直接转换，无需 OCR。
- 页码域、超链接域、页眉页脚、文本框和表格可能被线性展开到正文。
- DOC 与 DOCX 共用转换入口，但转换质量和可诊断性不同。
- 转成纯文本后通常丢失页码、表格结构和原始版式位置。

扩展名与签名不一致时，不得仅凭扩展名继续。签名能够明确证明为 Word 时可暂定为 W，但必须记录不一致证据并进入人工复核；签名也无法确认时归入 PX。

### 4.2 PT：文本型 PDF

**判定特征：**

- 文件签名和 MIME 证据共同支持 PDF。
- 大多数正文候选页能够直接提取足量、可读且顺序基本合理的文字。
- 空文本页比例较低，页面图片占比不构成主要内容来源。

**典型特点：**

- 无需 OCR，但提取文本保留的是页面绘制顺序，不等于法律段落语义。
- 分页硬换行、跨页句子、重复页眉页脚和页码会污染正文。
- 多栏、侧注或复杂排版可能导致阅读顺序错误。
- 页级文本可用于回溯问题，应在进入通用清洗前保留页边界。

### 4.3 PS：扫描型 PDF

**判定特征：**

- 文件签名和 MIME 证据共同支持 PDF。
- 大多数页面直接提取不到足量文字。
- 页面存在覆盖主要可视区域的图像，说明文字内容主要封装在扫描图像中。
- 直接提取结果与页面可见内容明显不相称。

**典型特点：**

- 必须经过中文 OCR 才能形成候选文本。
- 倾斜、模糊、印章覆盖和低对比度会降低识别质量。
- “第十一条”等结构标志中的汉字、数字和破折号易被误识别。
- OCR 页与页相互独立，跨页条文需要后续重组。
- 扫描件中的附件表格可能被错误线性化，但其内容不得进入正式语料。

### 4.4 PX：混合型或异常文件

满足任一条件时归入 PX：

- 部分页可直接提取足量文字，另一些正文候选页只能通过图像识别。
- 文件后缀、MIME 和签名相互冲突，且不能形成唯一可信结论。
- Word 转换成功但输出为空、严重乱码或与文件体量明显不相称。
- PDF 既缺少可用文本，又没有足以解释内容来源的页面图像。
- 提取顺序明显异常，无法安全判定为 PT。
- 文件损坏、加密、受密码保护或解析器无法读取。

PX 不是第四种自动提取器。它是停止自动处理并进入人工复核的兜底分类；后续可以由人工决定采用文本 PDF、OCR、重新获取源文件或拒绝导入。

## 5. 第二轴：内容结构分类

内容结构分类只能在产生候选文本后进行。对 PS 文件，必须先取得最低可用的 OCR 候选文本；不能在没有文字证据时根据文件名猜测 S 类别。

| 分类 | 内容特征 | 路由阶段用途 |
| --- | --- | --- |
| S1：纯法规正文 | 标题后进入章、节、条，正文结束后没有其他材料 | 以常规风险送入正文边界识别 |
| S2：复合发布文件 | 同一文件含通知、部门令、发布说明、修订决定或修改说明，再出现目标法规正文 | 标记前置材料风险，要求下游确认唯一目标法规 |
| S3：正文后附排除内容 | 法规正文后出现附件、评分表、文书模板或印发信息 | 标记尾部污染风险，要求下游在持久化前截断 |
| S4：正文与排除内容混合或边界不明 | 排除内容穿插正文，或无法确定目标正文的开始、结束 | 禁止自动进入正式语料，转人工复核 |

S 分类不改变提取器选择。例如 PT-S3 仍由文本型 PDF 提取器处理，W-S2 仍由 Word 提取器处理。它只向正文边界组件传递风险信号。

“附件”字样不能单独决定 S3。复合发布文件可能以“附件”形式承载目标法规正文；路由层只记录候选结构，不得看到“附件”即截断。

## 6. 格式探测与分类判定顺序

分类必须按以下证据顺序执行，后序证据不得掩盖前序冲突。

### 6.1 文件存在性与可读性

- 确认路径存在、是普通文件且可读。
- 计算来源文件摘要，作为本次分类证据的稳定标识。
- 原始文件只读，不移动、不改名、不写回。

文件不存在、不可读或不是普通文件时直接判定提取失败，不进入格式分类。

### 6.2 文件签名

- PDF 应以 `%PDF-` 等有效签名和解析器确认结果为准。
- DOC 应验证 OLE 复合文档签名及可读取的内部结构。
- DOCX 应验证 ZIP 容器和 WordprocessingML 核心项，不能只把任意 ZIP 当成 DOCX。

文件签名是格式判断的首要证据。扩展名只作为期望值和审计字段。

### 6.3 MIME 与扩展名交叉检查

- MIME 用于补充签名判断，不作为单一真相来源。
- 扩展名、MIME、签名一致时形成高置信格式结论。
- 任意两者冲突时记录冲突，不静默纠正。
- 签名明确且文件可正常解析时可以形成暂定分类；否则进入 PX。

### 6.4 Word 转换结果检查

对已确认的 Word 文件调用 Word 提取器，并至少检查：

- `textutil` 退出状态。
- 标准错误信息。
- 输出字节数和清洗前有效字符数。
- 中文、数字和法律结构标志的基本可读性。
- 输出是否为空、乱码或与源文件体量明显不相称。

转换成功只证明命令执行成功，不证明法律文本完整。结果异常时归入 PX，不得以“有非空文本”为由继续提交。

### 6.5 PDF 逐页探测

对每页分别采集以下指标：

- 去除空白后的有效字符数。
- 中文、数字和常用标点占比。
- 是否为低文本页。
- 页面图片数量及图片覆盖面积占页面面积的比例。
- 文本块的数量、位置和初步阅读顺序。

建议把“每页至少 40 个有效字符”作为首轮低文本页判定基线，但该数值必须可配置，并由真实法规样本校准。封面、空白页和仅含落款的页面不能单独决定整份文件类别。

### 6.6 PDF 文档级聚合

建议使用以下首轮判定基线：

- 可直接提取足量文字的页面比例不低于 80%，且低文本页能够由封面、落款或空白页合理解释：暂定 PT。
- 低文本页比例不低于 80%，且这些页面的主要图片覆盖率不低于 50%：暂定 PS。
- 两类页面均占有实质比例，或指标无法解释页面内容：判定 PX。

阈值不是提交门禁，也不能替代人工抽样。真实样本验证后可调整阈值，但必须保持“无法确定即 PX”的保守原则。

### 6.7 内容结构分类

完成物理提取后，使用标题、发布说明、条文标志、附件标题和尾部材料等信号形成 S1—S4 候选分类。最终正文边界仍由正文边界专项设计决定；路由层不得删除候选文本或宣称已确认法律效力版本。

## 7. 提取器共同输入契约

三个自动提取器接收同一份只读来源描述，至少包含：

| 字段 | 含义 |
| --- | --- |
| `source_path` | 原始文件绝对路径，只读 |
| `source_name` | 原始文件名，不等同于法规标题 |
| `source_digest` | 原文件内容摘要 |
| `declared_extension` | 文件扩展名，仅用于交叉检查 |
| `detected_media_type` | 由签名和 MIME 共同形成的真实格式结论 |
| `extraction_class` | W、PT 或 PS；PX 不进入自动提取器 |
| `classification_evidence` | 签名、MIME、逐页指标或转换探针等判定证据 |
| `run_id` | 本次处理标识，用于审计，不改变原文件 |

输入契约不得把 `document_id` 只绑定到扩展名或文件路径。法规身份和版本归属由总体设计及正文边界设计负责。

## 8. 提取器共同输出契约

自动提取器输出统一的“候选提取结果”，供正文边界组件消费：

| 字段 | 含义 |
| --- | --- |
| `source_digest` | 与输入对应的来源摘要 |
| `extractor_kind` | Word、文本 PDF 或扫描 PDF |
| `extractor_version` | 工具和适配器版本，用于复现 |
| `pages` | 按源顺序排列的页或逻辑页单元 |
| `text_blocks` | 保留页号、顺序和原始换行证据的候选文本块 |
| `warnings` | 格式冲突、低文本页、顺序异常、域代码等警告 |
| `metrics` | 字符量、空页比例、图片占比、OCR 置信度等提取指标 |
| `content_class_candidate` | S1—S4 候选及其证据 |
| `disposition` | 可继续、需要人工复核或提取失败 |
| `failure` | 失败阶段、错误类别和可读原因；成功时为空 |

共同约束如下：

- 输出必须保留来源顺序和页级定位，不能只返回一段无来源的纯文本。
- Word 缺少真实分页信息时，应明确标记逻辑页未知，不得伪造页码。
- OCR 输出必须保留块级置信度；不能只给整份文件一个平均分。
- 警告和指标只记录必要证据，不记录附件、评分表或文书模板的正文副本。
- 提取阶段为定位正文边界而读取到的排除内容只能在进程内短暂存在，不得写入正式或中间持久化产物，也不得写入日志。
- 只有正文边界组件确认的目标法规正文，才允许进入 `data/normalized/`、`data/structured/` 和 `data/chunks/`。

## 9. 各提取器职责

### 9.1 Word 提取器

Word 提取器负责：

- 调用现有 macOS `textutil` 转换 DOC/DOCX。
- 记录退出状态、错误输出、原始字符量和异常信号。
- 保留转换后的行序，标记无法恢复真实分页和表格结构的限制。
- 识别但不在本层最终处置 Word 域代码、页眉页脚和疑似表格线性化风险。

Word 提取器不得把 `textutil` 的零退出状态当作质量通过，也不得把表格线性化结果直接认定为法规正文。

### 9.2 文本型 PDF 提取器

文本型 PDF 提取器负责：

- 按页提取文字、文本块位置和初步阅读顺序。
- 保留分页边界和跨页重组所需证据。
- 识别重复页眉页脚、分页断行、多栏和顺序异常信号。
- 输出来源专属指标，不在本层执行最终法律段落切分。

提取器发现大量错序、乱码或不可解释的低文本页时，应把结果降级为人工复核，必要时重新分类为 PX。

### 9.3 扫描型 PDF 提取器

扫描型 PDF 提取器负责：

- 对页面图像执行必要的方向、倾斜和清晰度检查。
- 生成中文 OCR 候选文本、块位置和块级置信度。
- 保留页边界，标记印章覆盖、低清晰度和结构标志低置信风险。
- 识别正文页与疑似表格页的版式差异，但不保存排除内容正文。

OCR 结果是候选证据，不是权威法律文本。关键结构标志低置信、页面缺失或条文顺序异常时必须进入人工复核。

## 10. 现有机制的复用与差距

### 10.1 `resolve_explicit_sources`

**可复用：**

- 要求显式来源而不是无界扫描。
- 验证路径存在且不是目录。
- 在同一次输入中检测重复 `document_id`。
- 构造后续增量导入需要的来源对象。

**差距：**

- 只按后缀判断格式，未验证 MIME 和文件签名。
- 明确拒绝 PDF，类型契约也只允许 DOC/DOCX。
- 不产生分类证据、来源摘要和提取风险。
- 无法表达 PT、PS、PX 和人工复核结果。
- 当前编排还限制一次只导入一份文件，不能承担全量 `todo` 的任务清单职责。

新路由层应保留“显式输入和冲突前置失败”的原则，但不能直接复用其扩展名白名单作为真实格式判断。

### 10.2 macOS `textutil`

**可复用：**

- 当前 DOC/DOCX 转纯文本路径已存在并有测试覆盖。
- 无需在本阶段安装新的 Word 解析依赖。
- 对当前多数 Word 法规可生成非空候选文本。

**差距：**

- 硬编码为 macOS 系统工具，跨平台能力有限。
- 输出会丢失页面、表格、文本框和版式信息。
- 命令成功不代表文本完整或顺序正确。
- 不能处理 PDF，也不能区分正文和附件。
- 错误结果只形成普通标准化失败，缺少提取质量指标。

因此 `textutil` 继续作为 W 类底层转换器，而不是整个多格式路由器或质量判断器。

### 10.3 `clean_text`

**可复用：**

- 统一 CRLF、Unicode 换行、BOM、全角空格和连续空白。
- 删除现有规则覆盖的独立页码噪声与超链接域代码。
- 规范“编、章、节、条”标题间距。

**差距：**

- 当前在逐行清洗时删除空行，会丢失部分段落和版式证据。
- 只识别“第 N 页”，不能覆盖 `PAGE \\* MERGEFORMAT` 等 Word 页码域。
- 没有 PDF 重复页眉页脚、分页断行和阅读顺序修复能力。
- 没有 OCR 错字、低置信块和页面缺失处理能力。
- 对所有来源使用同一套清洗顺序，无法表达来源专属风险。

路由与提取阶段应先保留原始行序和页级证据，再调用可复用的通用清洗规则。来源专属清理及最终标准化由正文边界与中间格式设计约束，不能在提取器内无证据地删除文本。

## 11. 人工复核与失败边界

### 11.1 必须进入人工复核

- 文件被判定为 PX。
- 扩展名、MIME 和签名冲突，即使暂时可以读取。
- Word 转换输出非空但存在严重乱码、异常短文本或结构标志缺失。
- PDF 分类指标落在 PT 与 PS 之间，无法形成稳定结论。
- PDF 存在实质性的文字页与扫描页混合。
- 阅读顺序异常，可能改变条文语义。
- OCR 关键结构标志置信度低、正文候选页缺失或页序异常。
- 内容结构只能判为 S4。
- 提取器警告无法由自动质量规则证明安全。

人工复核前不得调用 append-only 提交。人工决定应记录所依据的页面和指标，但不得复制保存排除内容。

### 11.2 确定失败

- 文件不存在、不可读或已损坏。
- 文件受密码保护且没有合法可用的解锁输入。
- 真实格式不在当前支持范围。
- 提取器进程失败且没有可用候选结果。
- 来源文件摘要在处理过程中发生变化。

失败应记录阶段、稳定错误类别和可读原因，不得把工具堆栈或原始附件内容写入正式报告。

### 11.3 可以继续下游处理

只有同时满足以下条件才可继续：

- 真实格式结论明确。
- 自动提取器完成且候选文本达到最低可用标准。
- 页级或逻辑页级来源证据完整。
- 未命中强制人工复核条件。
- 已形成 S1—S3 候选分类；S4 不自动继续。

“可以继续”只表示可进入正文边界识别，不表示质量门禁已通过，更不表示允许提交。

## 12. 依赖和运行环境边界

- 本文不安装任何依赖，不修改 conda 环境。
- 所有后续 Python 代码和验证必须在 conda 环境 `fire` 中执行。
- Word 路径暂时复用系统 `/usr/bin/textutil`，无需新增 Python 包。
- 文本 PDF 解析器、PDF 页面渲染器、OCR 引擎和中文语言包尚未选型。
- 后续选型必须先查询候选工具的最新官方文档，并比较中文识别、页级坐标、置信度、离线运行、许可证和 macOS 兼容性。
- 网页研究必须使用 Firecrawl、Exa 或 Tavily MCP；不得改用通用网页搜索或抓取工具。
- 任何安装前必须向用户列出依赖、用途、安装位置和包管理工具，并获得明确批准。
- 后端依赖只能安装到 conda 环境 `fire`；具体使用 conda、pip 或其他工具须在实施计划中明确。前端不涉及依赖变更。

## 13. 设计验收条件

本文的设计成立需要满足：

- 任一来源文件都能依据证据落入 W、PT、PS 或 PX，不能以未知状态绕过人工复核。
- S1—S4 只承担内容风险路由，不与提取器类型混淆。
- 文件签名优先于扩展名，MIME 和扩展名只参与交叉验证。
- PDF 分类使用逐页字符量、低文本页比例和图片占比，而不是“一份 PDF 一个字符数”。
- 三类自动提取器遵守同一输入输出契约。
- 现有 `resolve_explicit_sources`、`textutil`、`clean_text` 的复用点和限制均被明确。
- 排除内容不进入正式语料、中间持久化产物或日志。
- 不确定提取结果在 append-only 提交前进入人工复核。
- 本设计不提前决定 OCR 技术栈，也不产生未经批准的依赖安装。
