# 目标法规正文边界与统一中间格式专项设计

**状态：** 已批准设计  
**日期：** 2026-06-28  
**角色：** `architecture_or_strategy` 总体架构下的专项分卷
**适用范围：** `法律文本/todo/` 多格式法规进入现有增量语料链路前的内容边界判定与中间数据契约
**上位设计：** [法规摄取总体架构](./2026-06-29-legal-ingestion-overall-architecture.md)

## 1. 文档职责

本文档唯一负责以下设计：

- 在一份源文件中确定目标法规标题、正文开始位置和正文结束位置；
- 区分纯正文、复合发布材料、正文后附排除内容以及混合不确定结构；
- 规定发布说明、修订说明、附件、评分表和文书模板的处理边界；
- 定义提取器输出到法律结构解析器之间的统一中间格式及其不变量；
- 说明边界不确定时为何必须阻止进入 append-only 提交流程。

本文档不负责文件格式探测、Word/PDF/OCR 提取器选型，不负责质量门禁阈值、批次状态机、人工复核操作步骤，也不负责当前 `todo` 文件的逐份评估结论。

## 2. 已确认范围

### 2.1 需要进入语料链路的内容

- 目标法规的正式标题；
- 编、章、节及其标题；
- 从第一条到最后一条的法规正文；
- 发布机关、公布日期、生效日期、修订日期和版本依据等结构化元数据；
- 用于回到原始文件核验正文的来源位置。

### 2.2 明确排除的内容

以下内容不参与检索，也不生成正文副本或其他保存产物：

- 附件；
- 评分表、考核表及其表格内容；
- 文书模板、文书式样及其填写说明。

提取报告只允许记录被排除内容的来源位置、类型和判定原因，不得记录被排除内容的标题或正文。原始源文件继续只读保留，必要时由核验人员回到源文件查看。

发布通知、发布说明和修订说明不作为可检索正文；其中能够确定目标法规身份和版本的事实，可以转写为结构化元数据，但不得把整段说明复制到正文产物。

## 3. 核心原则

1. **先定边界，后解析条文。** 未确认目标法规正文边界时，不得生成 `ParsedDocument`、chunk 或索引。
2. **只保存目标法规正文。** 正文中间产物不得先保存整份提取文本、再依赖下游忽略附件。
3. **源文件只读。** 不移动、不改写 `法律文本/` 下的文件；生成物与核验记录必须位于 `data/` 或约定的运行目录。
4. **证据组合优先。** 标题、第一条、条号连续性、终止条款、版式位置和后续内容类型必须联合判断，单一关键词不能决定边界。
5. **不确定即停止。** 自动规则不能唯一确定目标正文时，结果只能标记为待复核，禁止以猜测结果继续提交。
6. **排除内容最小留痕。** 系统只记录排除范围、类型和原因，不保存排除正文。

## 4. 内容结构分类

每份文件在格式提取分类之外，还必须获得一个内容结构分类。

| 类别 | 定义 | 典型结构 | 边界风险 |
| --- | --- | --- | --- |
| S1 纯正文 | 文件主体只有一个目标法规 | 标题 → 章/节 → 第一条至最后一条 | 标题误选、末条之后页脚污染 |
| S2 复合发布 | 文件包含发布通知、修订决定或说明，以及目标法规正文 | 发布/修订材料 → 目标法规标题 → 正文 | 把前置材料当正文，或把修订决定中的条文误认为目标正文 |
| S3 正文后排除 | 正文后还有附件、评分表或文书模板 | 目标法规正文 → 排除内容 | 排除内容并入最后一条 |
| S4 混合不确定 | 正文与非正文交错，或存在多个无法唯一判定的正文候选 | 多个标题/条文块交错，表格或模板穿插 | 不能通过单次首尾截断得到可靠正文 |

分类是对自动处理风险的描述，不直接等于处理结果。S1—S3 只有在边界证据完整时才可自动确认；S4 默认进入待复核。

## 5. 目标法规标题识别

### 5.1 标题候选

标题候选可以来自：

- 文件名去除扩展名后的规范化名称；
- 位于连续条文块之前、符合规章名称形态的独立文本行；
- 发布通知中明确指出的被发布、印发、修订或公布的法规名称；
- 修订材料之后再次出现、并直接引出第一章或第一条的法规名称。

标题候选必须排除机关名称、文号、日期、章节标题、附件标记和完整陈述句。

### 5.2 唯一目标标题的判定

目标标题必须同时获得下列证据中的多个：

- 与源文件名称中的法规名称一致或可解释地对应；
- 标题之后存在从第一条开始的主要连续条文块；
- 条文块的章节与终止条款构成完整法规结构；
- 发布或修订材料明确指向该名称；
- 没有另一个候选获得同等或更强的正文结构证据。

“第一条之前最后一个像标题的文本行”只能作为候选生成规则，不能作为最终判定规则。复合文件可能在修订决定中先出现若干条款，随后才出现目标法规标题与完整正文。

### 5.3 多个候选的处理

存在以下任一情况时，标题状态必须为 `review_required`：

- 两个或更多标题都连接完整条文块；
- 文件名与正文候选标题明显冲突；
- 只能依赖 OCR 低置信度文本识别标题；
- 无法判断文件保存的是法规全文、修订决定还是两者组合；
- 标题只出现在附件或模板区域。

## 6. 正文开始位置

正文开始位置是目标法规标题所在位置。进入可检索正文的首个结构单元通常是标题后的编、章、节或第一条。

发布机关、文号、发布日期和修订说明即使位于标题与第一条之间，也只进入目标元数据，不进入 `body_text`。如果标题后的元数据无法与正文区分，应保留来源位置并将边界标记为待复核。

自动确认正文开始位置至少要求：

- 已唯一确定目标法规标题；
- 在该标题之后找到第一条，或先找到合法的编、章、节后再找到第一条；
- 第一条之后存在可解释的连续条文结构；
- 目标条文块不是修订决定、附件说明或文书模板中的示例条文。

## 7. 正文结束位置

正文结束位置是目标法规最后一条正文的最后一个字符，不包括其后的空行、页眉页脚、印发信息或排除内容。

结束位置应综合判断：

- 条号连续性与最后一个正式条号；
- “本办法自……起施行”等终止性条款；
- 后续文本是否出现附件、附表、评分表、考核表、文书式样或印发信息；
- 页面或段落版式是否从法规正文切换为表格、表单或模板；
- 后续是否又出现一个独立且完整的法规正文候选。

“出现附件”只是内容类型信号，不能单独决定正文结束位置。只有当附件信号位于已确认目标正文之后，并且与最后一条形成稳定边界时，才能据此排除后续内容。

## 8. 不得见到“附件”就截断

`河北省消防设施管理规定.docx` 是该风险的明确案例。文件前部的修订材料可能出现“附件2”等文字，而目标法规全文位于这些材料之后。

若以首次出现“附件”为截断点，会同时造成：

- 目标法规标题被删除；
- 第一条至最后一条的正式正文全部丢失；
- 系统把发布或修订材料误认成目标内容；
- 后续仍可能生成非空产物，从而形成“成功但内容错误”的假阳性。

因此，排除顺序必须是：

1. 先唯一确定目标法规标题及其连续正文块；
2. 再确定该正文块的开始和结束位置；
3. 最后只排除已确认正文块之外的附件、评分表和文书模板。

此顺序是边界不变量，不得被基于关键词的前置截断覆盖。

## 9. 各类别的边界设计

### 9.1 S1 纯正文

- 以唯一标题和其后的第一条锁定开始位置；
- 以连续条文块及终止条款锁定结束位置；
- 最后一条后的页码、页脚和印发信息不进入正文；
- 若最后一条后仍有无法分类文本，不得自动确认边界。

### 9.2 S2 复合发布

- 发布通知、部门令、修订决定和说明先作为前置材料识别；
- 前置材料中的条号不得与目标法规条号合并计算；
- 目标法规必须由独立标题和完整连续条文块共同确认；
- 发布与修订材料只贡献可验证的机关、日期、版本依据等元数据；
- 无法区分“修订决定条文”和“修订后全文”时进入待复核。

### 9.3 S3 正文后排除

- 先按目标标题和正文结构确认法规正文；
- 再识别位于正文后的附件、评分表或文书模板；
- 排除区域不得进入标准化正文、结构化法规或 chunks；
- 提取报告只记录排除区域的页码、段落或块范围、类型与判定原因；
- 若排除内容穿插在最后一条内部，升级为 S4。

### 9.4 S4 混合不确定

以下情况均属于 S4：

- 正文与表格、模板交错；
- 多个法规正文候选无法唯一选择；
- OCR 导致条号、标题或页面顺序无法可靠恢复；
- 排除范围与正文范围重叠；
- 只能通过主观语义判断才能确定边界。

S4 不得自动生成可提交产物。人工复核只能确认边界或退回重新提取，不能用“尽可能多保留文本”的方式绕过边界要求。

## 10. 发布说明与修订说明

发布说明和修订说明具有版本证据价值，但不属于用户需要检索的法规正文。

允许形成的结构化事实包括：

- 发布机关；
- 公布日期；
- 生效日期；
- 修订日期；
- 修订决定名称或文号；
- 当前全文对应的版本依据。

每个事实必须带来源位置与提取状态。不能可靠确定的字段保留为空并产生诊断信息，禁止推测补全。说明原文不复制到 `body_text`、`articles` 或 chunks。

## 11. 统一中间格式

统一中间格式暂称 `LegalDocumentIntermediate`。它位于格式提取与现有法律结构解析之间，只承载目标法规正文及其边界证据。

### 11.1 顶层字段

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `schema_version` | 字符串 | 中间格式版本 |
| `document_id` | 字符串 | 当前语料链路中的文档标识 |
| `source_ref` | 对象 | 只读源文件引用与校验信息 |
| `extraction_class` | 枚举 | Word、文本型 PDF、扫描型 PDF 或异常混合类型 |
| `content_class` | 枚举 | `S1`、`S2`、`S3` 或 `S4` |
| `target` | 对象 | 目标法规身份与版本元数据 |
| `boundary` | 对象 | 正文首尾位置、状态与判定证据 |
| `body_text` | 字符串 | 仅含目标标题、层级标题和法规条文的规范文本 |
| `body_units` | 数组 | 正文文本单元及其源位置 |
| `diagnostics` | 数组 | 不含排除正文的警告和歧义说明 |
| `extraction_report` | 对象 | 提取结果和排除范围的最小审计记录 |

### 11.2 `source_ref`

| 字段 | 含义 |
| --- | --- |
| `source_path` | 原始文件的只读路径引用 |
| `source_name` | 原始文件名 |
| `source_sha256` | 绑定本次判定的源文件摘要 |
| `media_type` | 经真实类型探测得到的媒体类型 |
| `page_count` | 适用时记录原始页数 |

`source_ref` 不复制源文件。源文件摘要用于证明正文边界与哪一个源版本对应。

### 11.3 `target`

| 字段 | 含义 |
| --- | --- |
| `title` | 唯一确认的目标法规标题 |
| `issuing_authority` | 发布机关 |
| `region` | 适用地域 |
| `promulgated_on` | 公布日期 |
| `effective_on` | 生效日期 |
| `revision_events` | 修订日期、决定名称或文号及来源位置 |
| `version_basis` | 当前全文版本依据及来源位置 |

### 11.4 `boundary`

| 字段 | 含义 |
| --- | --- |
| `status` | `confirmed`、`review_required` 或 `rejected` |
| `start` | 目标标题在源文件中的页、段落、行或文本块位置 |
| `end` | 最后一条正文最后字符的来源位置 |
| `title_evidence` | 支持标题判定的证据类型与位置 |
| `start_evidence` | 支持正文开始判定的证据类型与位置 |
| `end_evidence` | 支持正文结束判定的证据类型与位置 |
| `ambiguities` | 尚未消除的候选冲突，只记录描述和位置 |

### 11.5 `body_units`

每个正文单元至少包含：

- `unit_id`：中间格式内稳定的单元标识；
- `kind`：`title`、`part`、`chapter`、`section`、`article` 或 `paragraph`；
- `text`：该正文单元文本；
- `source_span`：其在原始文件中的来源位置；
- `parent_unit_id`：适用时指向上级结构单元。

`body_units` 用于保留来源位置，不替代最终的 `ParsedArticle`。

### 11.6 `extraction_report`

提取报告至少包含：

- `status`：本次提取与边界判定状态；
- `excluded_ranges`：每个排除范围的开始位置、结束位置、类型和判定原因；
- `warnings`：文本缺页、顺序异常、OCR 歧义等诊断；
- `source_coverage`：正文覆盖的源页面或文本块范围。

`excluded_ranges` 禁止包含排除区域的标题、摘要、正文、OCR 文本或表格内容。

## 12. 中间格式不变量

1. `boundary.status` 不是 `confirmed` 时，禁止生成正式 structured、chunks 和索引产物。
2. `body_text` 必须非空，且只由 `body_units` 中允许的正文类型按顺序组成。
3. `body_text` 必须包含唯一目标标题和至少一个正式条文。
4. `body_units` 的来源位置必须单调、可回溯且位于 `boundary.start` 与 `boundary.end` 之间。
5. 任何 `excluded_ranges` 都不得与正文来源范围重叠。
6. 附件、评分表和文书模板的文字不得出现在 `body_text`、`body_units`、`diagnostics` 或 `extraction_report` 中。
7. 发布与修订说明不得出现在 `body_text`；由其形成的元数据必须保留来源位置。
8. 目标标题存在竞争候选、正文首尾不唯一或条文块归属不明时，`boundary.status` 必须是 `review_required`。
9. 源文件摘要变化后，既有边界判定不得继续视为有效。
10. 中间格式本身不表示允许提交；它还必须通过质量门禁专项设计定义的检查。

## 13. 与现有机制的差距

| 现有组件 | 当前能力 | 与本设计的差距 |
| --- | --- | --- |
| `normalize_document` | 用 `textutil` 提取并清理整份 Word 文本，直接写入 normalized | 没有内容分类、正文边界、源位置和排除契约；会保存附件等整份文本 |
| `ParsedDocument` | 保存标题、机关、地域、公布/生效日期和条文列表 | 没有源文件摘要、内容分类、边界状态、版本依据、修订事件和排除记录 |
| `ParsedArticle` | 保存条号、章节路径和条文文本 | 没有来源位置；不能证明条文是否来自已确认正文范围 |
| `parse_legal_document` | 从文本候选中选标题并按编章节条解析 | 默认处理全部输入；最后一条后的普通文本会继续并入该条；无法区分目标正文与附件 |
| `build_chunks` | 信任 structured 并按条文生成检索块 | 不检查边界状态，也无法识别附件或模板污染 |
| 增量语料生成 | `normalize → parse → write structured → build chunks` | 在解析和切块前没有“边界已确认”的阻断点，非空 chunk 会掩盖内容错误 |

本设计要求统一中间格式成为格式提取与 `ParsedDocument` 之间的输入契约。现有 `ParsedDocument` 和 `ParsedArticle` 可以继续作为下游法律结构，但其输入只能来自 `boundary.status=confirmed` 的 `body_text/body_units`。

## 14. 提交阻断规则

出现下列任一情况，必须阻止逐文件 append-only 提交：

- 目标法规标题不唯一；
- 正文开始或结束位置不唯一；
- 正文与排除范围重叠；
- 文件属于未解决的 S4；
- 目标条文块可能来自附件、修订决定或文书模板；
- 排除内容已经进入任一待提交产物；
- 源文件摘要与边界判定时不一致；
- 中间格式不满足任一不变量。

阻断时不得生成正式 `data/normalized/`、`data/structured/`、`data/chunks/` 或索引增量。staging 中若存在候选产物，也只能作为失败运行的临时数据按批次规则清理，不能发布为正式语料。

## 16. 设计结论

多格式适配不能止于“把文件转换成非空文本”。系统必须先从源文件中唯一确认目标法规正文，再把仅含正文的统一中间格式交给现有结构解析与切块链路。

附件、评分表和文书模板既不检索，也不生成保存产物；系统只保留其排除位置、类型和原因。任何边界歧义都必须在 append-only 提交前显式停止，避免把不可覆盖的错误内容写入正式语料。
