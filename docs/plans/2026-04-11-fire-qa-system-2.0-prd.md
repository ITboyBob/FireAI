## 产品定位与能力基线

消防问答系统 2.0 是一个面向本机单用户的消防法规问答产品。它基于仓库内 `法律文本/` 的消防法规资料，通过离线建库和在线检索回答用户问题，但它不是法律裁判系统，也不提供高风险法律意见替代。

本产品必须保持以下产品级能力基线：

- 用户可以围绕消防法规直接发起问题，并在同一会话中继续追问。
- 系统回答必须基于已建好的法规检索证据，而不是绕过检索直接让大模型自由发挥。
- 回答结果必须让用户能看到结论、法律依据、条款原文和必要的修正提示。
- 当证据不足、索引缺失或模型调用失败时，系统必须明确告知用户当前失败类型，而不是给出不可靠的伪答案。
- 历史会话必须能在本机恢复，用户刷新对话页或重新打开历史会话时，不应因为浏览历史而触发新的模型调用。

从产品视角看，旧的一期 RAG 设计提供了“语料可处理、证据可检索、回答可约束”的底座；2.0 在此基础上正式升级为“首页发起、对话承接、证据核对、连续追问”的问答产品。

## 问题陈述

当前系统虽然已经具备会话 API、多轮上下文和本机持久化基础，但前端产品层存在明显缺口，已经不是“样式不够好看”的问题，而是**页面模型和交互契约没有被产品文档固定**的问题：

- 当前根页面同时承担“首页”和“对话页”两种职责，导致首屏信息架构混乱。用户打开页面后看到的是“历史会话管理壳”，而不是可直接发起问答的产品首页。
- 当前首页 `Starter Cards` 没有被定义为正式首页组件，只是被临时放进线程空状态里，结果前端空状态渲染一覆盖，卡片就会被吞掉。
- 当前 `textarea` 没有正式的键盘交互约束，用户按 `Enter` 只会换行，不能形成“输入后立即发问”的基本问答体验。
- 当前“从首页输入问题进入对话”的跳转链路没有被定义成正式产品行为。即使后台正在处理，前端也没有立即切换到对话态、没有用户消息落位、没有等待中的助手占位，因此用户感知为“没有任何变化”。
- 当前系统尚未接入 WebSocket / SSE 流式输出，但前端把“没有流式”错误地等同于“可以没有即时反馈”。这是一条错误前提。即使本期仍是非流式架构，前端也必须在提交后立即表现出页面跳转和处理中状态。
- 当前视觉层没有明确区分“首页启动面板”和“对话证据面板”，导致实现者很容易把两种页面继续做成一个混杂壳，既不符合你给出的参考图，也不利于后续测试和验收。
- 当前产品文档没有把“什么是首页”“什么是对话页”“哪些元素必须存在”“哪些能力本期不能假装支持”写清楚，导致实现者可以在技术上“返回了 200”，但在产品上仍然是未完成状态。

从用户视角看，问题不是“系统不能回答问题”，而是“系统没有形成一个明确的问答产品流程：进入首页、输入问题、跳转到对话页、看到处理中、拿到回答、继续追问”。

## 解决方案

本期将当前系统前端正式收敛为**两个产品页面态 + 一条明确的发问跳转链路**：

1. `首页态`
   - 负责启动问答，不承载历史消息流。
   - 采用你给出的图 3 那种“深色 command center”方向：左侧为品牌和最近会话，右侧为英雄区、输入框和能力卡片。
   - 首屏必须让用户清楚知道“现在可以直接输入问题”。

2. `对话态`
   - 负责展示当前会话的消息流、修正提示、法律依据和证据区。
   - 采用你给出的图 2 那种“浅色 evidence desk”方向：左侧仍保留会话导航，右侧重点展示提问、回答、法律依据和证据卡片。
   - 进入对话态后，页面重心必须从“引导发问”切换为“理解和核对证据”。

3. `首页 -> 对话页` 跳转链路
   - 用户在首页输入并发送问题后，系统必须先创建或确定当前会话，再显式切换到对话态。
   - 即使本期没有流式输出，也必须立即渲染用户消息和“助手处理中”占位，不允许界面静止等待。
   - 当后端返回后，再把占位替换成正式回答、法律依据和证据区。

4. `继续追问` 链路
   - 用户进入对话态后，`Enter` 发送、`Shift+Enter` 换行。
   - 每次提问都重新检索最新证据，但前端必须让用户感知到“我仍在同一会话中继续追问”。

5. `产品真实能力约束`
   - 本期没有 WebSocket / SSE 流式输出。
   - 本期没有附件上传。
   - 本期没有多标签页实时同步。
   - 因此前端不得用可点击入口、假图标或假交互暗示这些能力已经可用。

本期的目标不是像素级复刻参考图，而是把参考图背后的**结构、层次、状态跃迁和交互纪律**落成可以执行和测试的产品约束。

## 用户故事

1. 作为首次进入系统的本机用户，我希望打开页面时先看到一个明确的问答首页，而不是历史管理后台，这样我知道第一步该做什么。
2. 作为首次进入系统的本机用户，我希望首页中央就有可输入问题的主输入框，这样我不用先理解会话列表才能开始提问。
3. 作为首次进入系统的本机用户，我希望首页展示若干预设问题卡片，这样我可以快速试用系统支持的能力方向。
4. 作为首次进入系统的本机用户，我希望这些预设问题卡片稳定可见，而不是被某段前端空状态逻辑覆盖掉，这样首页不会显得像坏掉了一样。
5. 作为中文输入法用户，我希望输入法联想期间按 `Enter` 不会误发送消息，这样不会在选词时把半句话发出去。
6. 作为键盘用户，我希望在输入框中按 `Enter` 直接发送，而按 `Shift+Enter` 只换行，这样连续提问更顺手。
7. 作为发起新问题的用户，我希望发送后立即从首页切换到对话页，这样我知道系统已经接受了我的问题。
8. 作为发起新问题的用户，我希望对话页第一时间显示我的问题气泡，这样我能确认系统收到的内容是什么。
9. 作为发起新问题的用户，我希望在回答返回前就看到“正在检索和生成回答”的占位区域，这样即使不是流式输出也不会误以为系统卡死。
10. 作为等待回答的用户，我希望在等待过程中发送按钮和重复提交行为被合理约束，这样不会因为多次连按造成重复请求。
11. 作为查看结果的用户，我希望对话页把回答、修正提示、法律依据和证据区分层展示，这样我能快速定位结论与依据。
12. 作为查看结果的用户，我希望法律依据以清晰标签或条目形式展示，而不是埋在长段文本里，这样更容易扫读。
13. 作为查看结果的用户，我希望证据区以卡片形式展示条文原文，而不是普通纯文本堆叠，这样更方便核对。
14. 作为继续追问的用户，我希望在对话页底部一直保留输入区，这样我不用滚回顶部才能提问。
15. 作为继续追问的用户，我希望继续提问时页面不要退回首页，而是停留在当前对话页，这样连续交流不会被打断。
16. 作为查看历史会话的用户，我希望左侧最近会话列表来自真实会话数据，而不是硬编码示例项，这样列表才可信。
17. 作为查看历史会话的用户，我希望点击左侧会话即可进入对应对话页，并恢复该会话历史，这样我可以继续之前的话题。
18. 作为查看历史会话的用户，我希望仅仅打开历史会话不会触发新的模型调用，这样浏览历史不会产生额外成本和副作用。
19. 作为刷新页面的用户，我希望刷新某个对话页后仍能回到同一会话，这样 URL 可以承担真正的页面定位作用。
20. 作为使用浏览器前进后退的用户，我希望首页和对话页之间的切换能被历史记录正确感知，这样浏览器导航不会失真。
21. 作为删除会话的用户，我希望删除当前会话后页面明确回到首页态或安全的空态，而不是停在一个失效会话上。
22. 作为没有任何历史记录的用户，我希望首页依然完整可用，而不是被空列表和管理按钮占满。
23. 作为阅读答案的用户，我希望修正提示是显式信息块，而不是混入正文的一小行字，这样我能意识到系统改判了依据。
24. 作为阅读答案的用户，我希望当本轮依据变化时，证据区随之切换到最新证据，而不是继续显示旧证据，这样前后逻辑才一致。
25. 作为本机用户，我希望首页和对话页视觉风格有明确区分，这样我能一眼看出自己当前处在“发起任务”还是“审阅证据”阶段。
26. 作为本机用户，我希望主要界面文案以中文为主，这样不会把本来就偏技术的系统又做成英文后台。
27. 作为本机用户，我希望英文大写标题只作为辅助视觉标签，而不是承担主要信息表达，这样整体界面不会失去本地可用性。
28. 作为维护者，我希望首页态和对话态是正式产品概念，而不是一个页面里临时拼出的两个 if/else，这样后续实现不容易继续失焦。
29. 作为维护者，我希望“首页组件”和“线程空状态组件”被明确区分，这样不会再发生 Starter Cards 被错误吞掉的问题。
30. 作为维护者，我希望输入框行为、跳转行为、等待行为被写成明确契约，这样后续实现和测试都能精确判断是否完成。
31. 作为维护者，我希望即使不引入新前端框架，也能通过明确的页面状态机完成产品目标，这样不会把架构问题误判为“必须换 React 才能修”。
32. 作为维护者，我希望参考图只约束产品层结构和视觉方向，而不是逼着实现去做不可维护的像素级复刻，这样开发与验收标准才合理。
33. 作为开发者，我希望首页输入后进入对话页的行为有明确的 URL 约束，这样刷新、深链和浏览器返回都能一致工作。
34. 作为开发者，我希望非流式情况下的等待态也有明确 UI 契约，这样不会再把“没有流式”当作“什么都不显示”的借口。
35. 作为开发者，我希望前端不为未实现能力预留可点击入口，这样不会制造新的产品欺骗和后续返工。

## 产品决策

### 一、产品边界

- 产品定位仍然是“消防问答系统 2.0”，不是本期内直接实现的自主规划 Agent。
- 本期仍然是本机单用户产品，不引入账户体系、权限模型和多端同步。
- 本期前端重构的核心目标不是新增算法能力，而是把已有 RAG 和会话能力包装成**完整、可感知、可验收**的产品流程。
- 本期不改变消防法规语料来源，仍以仓库内 `法律文本/` 及其离线建库产物作为回答依据。
- 在线问答不能在用户等待回答时临时重建索引；若建库产物缺失，产品必须进入明确的“建库未完成”错误态。
- 证据不足时必须拒答或提示不足，不得为了维持“看起来能回答”的体验而输出无依据结论。
- 当前没有 WebSocket / SSE 流式输出，但前端必须具备非流式即时反馈能力。
- 当前没有附件上传，因此参考图中的附件视觉语言若被保留，也只能是不可点击的占位装饰；更推荐本期直接不暴露该入口。

### 二、页面与路由模型

- 前端必须显式区分两个页面态：
  - `首页态`：负责发起问题。
  - `对话态`：负责展示当前会话。
- 产品行为上必须至少支持两个 URL：
  - `/` 对应首页态。
  - `/conversations/{conversation_id}` 对应对话态。
- 即使短期仍然复用同一套 HTML 模板或同一份静态资源，**产品契约上也必须表现为两个明确页面**，不能继续把“有没有 activeConversationId”当作全部页面模型。
- 首页发送首条问题时，系统必须先建立会话，再进入 `/conversations/{conversation_id}`。
- 点击历史会话时，系统必须进入对应 `/conversations/{conversation_id}`，并恢复该会话详情。
- 删除当前打开的会话后，系统必须离开失效会话 URL，回到 `/` 或其他有效会话 URL。

### 三、首页态约束

- 首页视觉方向参考你给出的图 3：深色、集中、带“command center”气质，但不得直接照抄英文文案。
- 首页主区域必须包含：
  - 视觉标题区
  - 主输入框
  - 发送入口
  - 预设问题卡片
  - 最近会话/最近调查入口
- 首页主区域不得展示历史消息流、法律依据列表或证据卡片，这些属于对话态职责。
- `Starter Cards` 是首页一级组件，不得挂靠在线程空状态的附属渲染里。
- 点击预设问题卡片的默认行为为：填充输入框并聚焦输入，而不是静默触发请求。
- 当系统没有任何历史会话时，首页仍然完整成立；“空列表”只能影响左侧列表，不得破坏首页主体。

### 四、对话态约束

- 对话态视觉方向参考你给出的图 2：浅色、留白更多、重点突出证据和结构化信息。
- 对话态必须包含：
  - 当前问题消息
  - 助手回答区
  - 修正提示区（在需要时显示）
  - 法律依据区
  - 证据区
  - 底部持续可用的输入区
- 证据区应以卡片或块级证据模块展示，不得退化为普通无层次长文本。
- 修正提示必须是独立提示块，不得只用一句颜色很淡的辅助文案草草带过。
- 对话态允许出现空会话，但空会话占位不得复用首页 Hero 和 Starter Cards，以免再次混淆首页态与对话态。

### 五、输入框与键盘交互契约

- `Enter` 发送消息。
- `Shift+Enter` 换行。
- 当事件处于输入法组合态时，不得因为 `Enter` 而发送消息；必须等待组合态结束。
- 空白消息不得提交。
- 提交进行中时，发送按钮和重复键盘发送应被抑制，避免同一输入被连发。
- 若请求失败，输入框中的原始用户输入不应被无条件丢弃；用户应能看到失败并继续编辑或重试。

### 六、非流式等待态契约

- 本期明确不实现逐字流式输出。
- 但用户点击发送后的即时反馈必须至少包括：
  - 页面切换到对话态
  - 用户消息立即落位
  - 助手处理中占位块立即出现
  - 顶部或底部状态文案明确显示“正在检索最新证据并生成回答”
- 不允许出现“按钮点了但页面完全不变，只能凭感觉等”的状态。
- 不允许用伪流式打字动画冒充真实流式能力。
- 若后端返回错误，占位块必须切换为错误态，并给出明确原因类型，例如模型失败、会话不存在、建库未完成。

### 七、交互职责边界

- 产品必须继续支持会话创建、读取、重命名、删除和发送消息这些用户动作。
- 首页发送首条问题时，用户感知上必须是一个连续动作：提交问题、进入对话页、看到自己的问题和处理中占位。
- 仅打开历史会话时，只能恢复既有详情，不得产生新的回答、轮次或模型调用。
- 首页态与对话态必须在页面行为上清晰区分；检索、回答生成和证据组织必须作为系统能力稳定产出，而不是依赖用户在界面上手工拼接。

### 八、视觉与文案约束

- 首页和对话页必须采用不同但同属一套品牌体系的视觉层次：
  - 首页更像启动台。
  - 对话页更像证据审阅台。
- 主文案默认使用中文；英文可作为辅助标签或品牌装饰，不得承担主要操作说明。
- 左侧会话导航在两个页面态中都应稳定存在，形成统一产品骨架。
- “最近调查 / 最近会话”必须来自真实会话数据，不得用静态占位长期冒充。
- 如果某个视觉元素当前没有真实能力支撑，就不应被渲染成一个看起来能点击的正式控件。

## 测试决策

- 产品验收只关心外部行为，不绑定内部实现细节。前端验收重点是“用户是否真的完成了页面跳转、输入、等待和恢复”，而不是“内部调用了哪个 DOM 辅助函数”。
- 本期前端重构至少需要覆盖以下行为：
  - 首页态是否渲染首页骨架而不是旧的历史管理首屏。
  - `Starter Cards` 是否在首次进入首页时稳定可见。
  - 点击预设问题卡片后是否正确填充输入框。
  - `Enter` 是否发送、`Shift+Enter` 是否换行、输入法组合态下 `Enter` 是否不会误发。
  - 首页发送首条问题后是否进入对话态，并显示用户消息与处理中占位。
  - 对话态加载历史会话时是否只读取详情而不触发新模型调用。
  - 删除当前会话后是否正确离开失效会话页面。
  - 刷新对话页后是否仍能恢复到同一会话。
  - 非流式等待态是否在真实延迟下仍然让用户感知到系统正在工作。
- 本期还必须覆盖 RAG 产品底线：
  - 有证据时，回答必须展示可核对的法律依据和条款原文。
  - 证据不足时，必须明确拒答或提示不足。
  - 索引缺失时，必须提示建库未完成。
  - 追问导致依据变化时，必须展示修正提示并切换到最新证据。
- 在浏览器自动化测试依赖未正式纳入仓库前，至少要通过真实浏览器手工验收完成以下检查：
  - 首页按 `Enter` 能发送、`Shift+Enter` 能换行。
  - 首条问题发送后页面确实切到对话页。
  - 无流式情况下仍能看到处理中占位。
  - 刷新对话页后会话仍可恢复。

## 非本期范围

- WebSocket、SSE 或逐字流式回答。
- 附件上传、图片上传、拖拽上传和 OCR 工作流。
- 多用户账号、权限体系、共享会话和协作编辑。
- 会话搜索、标签、收藏、导出和批量管理。
- 多标签页实时同步和跨设备同步。
- 真正的前端 SPA 框架迁移；本期不把“换框架”当作默认解法。
- 参考图的像素级复刻；本期追求的是结构、层次和体验对齐，不是视觉一比一还原。
- 自动法律裁判、高风险法律建议、法律责任结论替代。
- 知识图谱、三元组联动、微调、重排训练和多 Agent 自动规划。

## 补充说明

- 这次修订明确挑战了两个错误前提：
  - 没有流式输出，不等于可以没有即时页面反馈。
  - 页面不好用，不等于必须先上更重的前端框架。
- 当前前端的主要问题是页面状态机和产品边界缺失，而不是 API 不存在。
- 本 PRD 修订完成后，下一步不应直接继续在旧前端逻辑上零碎打补丁，而应先同步更新 2.0 实施计划，把“首页态 / 对话态 / URL / 键盘规则 / 等待态 / RAG 产品底线 / 验收步骤”拆成可执行任务。
