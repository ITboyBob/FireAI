# 消防问答系统 2.0 PRD

**文档目标：** 将当前“消防法律 RAG 验证面板”升级为“消防问答系统 2.0”，在保留现有离线建库与检索能力的前提下，增加本机持久化会话、历史对话管理和多轮上下文能力，并为未来升级到更强的问答 Agent 预留演进空间。

**文档状态：** 草案已基于当前会话中的已批准设计结论拟写，可作为下一阶段实施计划的输入。

## 问题陈述

当前系统已经具备单轮消防法律问答能力，但仍然停留在“极薄验证面板”阶段，存在以下问题：

- 用户无法查看历史对话，刷新页面或重启服务后无法继续之前的交流。
- 系统缺少正式的会话实体和消息持久化机制，在线链路本质上仍是一次性无状态问答。
- 用户无法顺畅进行多轮追问，像“上一条提到的第二条是什么”“这个规定在河北适用吗”这类上下文依赖问题缺少稳定支持。
- 现有前端更像技术验证页，而不是可持续使用的本地问答产品界面。
- 如果未来直接从当前结构硬扩展到 Agent，容易把“历史会话”“上下文管理”“自主规划”混在一起，造成架构失焦。

从用户视角看，问题不是“现在不能回答问题”，而是“现在还不能像一个真正可持续使用的本地问答系统那样工作”。

## 解决方案

本期产品将当前系统升级为“消防问答系统 2.0”，定位为**本机单用户、会话持久化、多轮上下文感知的消防法规问答系统**，而不是立即升级为具备自主规划能力的 Agent。

用户将获得以下能力：

- 进入页面后可以查看历史会话，并从历史会话继续追问。
- 新建、重命名、删除会话，重启服务后仍可恢复。
- 系统能够识别基础追问场景，在保留上下文连续性的同时，始终基于最新知识库重新检索。
- 长会话下，系统使用“最近 N 轮对话 + 更早历史摘要”的方式控制上下文长度。
- 助手消息界面只展示“回答”和“法律依据”。
- 证据区域只展示法律条款原文，不展示调试信息。
- 当本轮最新检索证据推翻前文时，系统以最新证据为准，并在用户侧明确提示本轮已修正前文。

系统将继续保留当前项目的核心原则：

- 检索与证据约束优先于会话连续性。
- 历史摘要只用于话题连续性线索，不作为法律依据。
- 追问场景下也不跳过重新检索。
- 可扩展性来自清晰分层和稳定接口，而不是过早引入 Agent 执行状态机。

## 用户故事

1. 作为一名本机使用者，我希望打开网页后能看到历史会话列表，以便快速回到之前讨论过的问题。
2. 作为一名本机使用者，我希望新建一个全新会话，以便把不同法律问题分开管理。
3. 作为一名本机使用者，我希望系统能为新会话自动生成默认标题，以便会话列表不会充满无意义的空标题。
4. 作为一名本机使用者，我希望手动重命名会话，以便用自己更容易理解的方式整理问题主题。
5. 作为一名本机使用者，我希望删除不再需要的会话，以便保持会话列表整洁。
6. 作为一名本机使用者，我希望服务重启后仍能看到历史会话，以便不用重新问一遍已经问过的问题。
7. 作为一名本机使用者，我希望打开历史会话后能直接继续追问，以便围绕同一个法规主题连续交流。
8. 作为一名本机使用者，我希望系统理解“上一条”“第二条”“这个规定”“它”等基础指代，以便不用每次都重复完整法规名称。
9. 作为一名本机使用者，我希望追问时系统能保留话题连续性，但仍然重新检索最新证据，以便降低旧上下文污染新回答的风险。
10. 作为一名本机使用者，我希望长对话不会因为上下文过长而明显变慢或失稳，以便持续使用同一会话。
11. 作为一名本机使用者，我希望助手消息只展示回答和法律依据，以便界面更聚焦、更容易阅读。
12. 作为一名本机使用者，我希望证据区只展示法律条款原文，以便快速核对答案所依据的法规内容。
13. 作为一名本机使用者，我希望在追问场景下优先看到与上一轮相关联的法律条款原文，以便理解当前回答和上文之间的关系。
14. 作为一名本机使用者，我希望当本轮检索依据已经变化时，系统改为展示本轮最新条款原文，以便看到真正支撑当前回答的依据。
15. 作为一名本机使用者，我希望当系统根据新证据修正前文时，界面能明确提示，而不是悄悄改口，以便理解为什么前后表述不同。
16. 作为一名本机使用者，我希望知识库更新后，历史消息仍保留原始回答快照，以便回看当时系统是如何回答的。
17. 作为一名本机使用者，我希望在旧会话中继续提问时，系统默认基于最新知识库回答，以便得到更新后的法规依据。
18. 作为一名本机使用者，我希望当证据不足时系统明确拒答，以便避免把不可靠内容误当成法律结论。
19. 作为一名本机使用者，我希望当建库未完成时系统给出明确提示，以便知道问题在环境或数据，而不是误以为是模型胡说。
20. 作为一名本机使用者，我希望模型失败和证据不足被区分开，以便理解这次失败是技术问题还是知识问题。
21. 作为一名本机使用者，我希望打开会话列表或浏览历史消息时不触发新的模型调用，以便快速查看历史且不产生额外成本。
22. 作为一名本机使用者，我希望系统在会话内部维持一致的阅读结构，以便不同轮次的回答都能快速比对。
23. 作为一名开发者，我希望在线链路被明确拆分为会话管理、上下文管理、检索编排和回答生成，以便后续迭代不会把单轮接口堆成巨石。
24. 作为一名开发者，我希望会话存储层与知识库检索层解耦，以便未来更换存储或检索实现时不会牵动整条链路。
25. 作为一名开发者，我希望追问判定模块可以替换或优化，但“始终重新检索”的产品规则在本期保持稳定，以便在迭代中控制风险。
26. 作为一名开发者，我希望历史摘要模块只暴露稳定的输入输出接口，以便可以独立测试和替换摘要策略。
27. 作为一名开发者，我希望回答快照作为正式产品数据被持久化，以便后续排查“为什么这轮和上一轮不同”时有据可查。
28. 作为一名开发者，我希望每轮对话都记录知识库版本，以便在语料更新后定位回答和知识库之间的关系。
29. 作为一名开发者，我希望前端展示结构与后端内部调试数据解耦，以便界面保持简洁，同时仍保留必要的运行元数据。
30. 作为一名维护者，我希望本期架构为未来升级到更强的问答 Agent 留出空间，以便后续新增规划层时不需要推翻会话模型。

## 实现决策

- 产品定位固定为“消防问答系统 2.0”，不是本期内直接实现的自主规划 Agent。
- 第一阶段使用场景固定为“本机单用户”，不引入账号、权限、租户隔离和多人协作模型。
- 系统继续保留现有离线建库能力，离线链路不直接感知会话。
- 在线部分从无状态单轮问答升级为“会话感知应用层”，在检索与回答能力之上新增会话管理与上下文管理能力。
- 持久化方案采用本机 `SQLite`，用于保存会话、消息、轮次元数据、回答快照、会话摘要和知识库版本。
- 会话是一级产品实体，必须支持创建、读取列表、打开详情、重命名和删除。
- 消息与轮次元数据分离建模：消息面向用户展示；轮次元数据面向系统内部运行与追踪。
- 在线应用层至少包含以下深模块：
  - `ConversationRepository`：封装会话、消息、快照和摘要的本地持久化读写。
  - `ConversationService`：封装会话生命周期行为，包括创建、重命名、删除、恢复和排序。
  - `TurnClassifier`：判断当前输入是否属于追问，并提取追问所需的连续性线索。
  - `ContextManager`：负责“最近 N 轮 + 更早历史摘要”的上下文组装、裁剪和降级策略。
  - `ConversationSummaryManager`：负责会话摘要生成、更新和读取，供长会话使用。
  - `RetrievalOrchestrator`：在多轮场景下执行上下文增强后的查询构造，并始终触发重新检索。
  - `AnswerComposer`：负责将本轮回答、法律依据、条文原文和修正提示整理为前端展示结构与持久化快照。
  - `KnowledgeVersionResolver`：为每轮回答附加知识库版本标识。
- 追问判定的第一阶段职责被严格限制为：
  - 判断当前输入是否依赖前文；
  - 抽取前文中的法规对象、条号、地域、时间范围和指代线索；
  - 为本轮重新检索构造更完整的查询输入。
- 追问判定在本期不负责决定是否跳过检索，也不允许直接复用旧答案或旧引文作为当前回答依据。
- 多轮上下文规则固定为“最近 N 轮对话 + 更早摘要”，其中 `N` 为配置项，不写死在产品需求里。
- 历史摘要只用于话题连续性线索，不作为法规依据，不可直接替代本轮检索结果。
- 回答正确性的最高优先级仍然是本轮最新检索证据；如果与历史内容冲突，必须以本轮最新证据为准。
- 若本轮最新证据修正前文，前端需展示明确修正提示，后端也需保存相应的修正标记。
- 历史会话保留原始回答快照；但在旧会话中继续追问时，系统默认基于最新知识库重新检索和回答。
- 前端产品形态升级为双栏结构：左侧会话列表，右侧当前会话消息流与输入区域。
- 前端用户侧展示结构收敛为：
  - 助手消息只展示“回答”和“法律依据”；
  - 证据区只展示法律条款原文；
  - 若本轮修正前文，则展示修正提示。
- 追问场景下，条款原文展示优先关联上一轮相关条文；但如果本轮重新检索后依据变化，则必须改为展示本轮最新条文原文。
- 对话执行接口与会话管理接口分离，避免单一聊天接口承担全部会话职责。
- 一轮消息的后端处理顺序固定为：校验会话、持久化用户消息、判定追问、组装上下文、构造查询、重新检索、生成回答、检测是否修正前文、持久化快照与元数据、返回前端最小展示结构。
- 前端读取会话列表和历史消息时不得触发新的模型调用或检索调用。
- 后端内部仍需保存必要的运行元数据，包括是否追问、是否使用摘要、知识库版本、是否修正前文和失败类型，即使这些字段不直接展示给用户。
- 错误类型至少区分为：建库未完成、证据不足、模型失败、会话不存在或已删除、摘要不可用降级。
- 当摘要不可用或摘要生成失败时，系统应降级为仅使用最近 N 轮，不得因此让会话整体不可用。
- 可扩展性约束如下：
  - 会话存储与知识库检索解耦；
  - 追问判定器可替换；
  - 回答快照对产品稳定；
  - 若未来升级为真正 Agent，应在当前会话应用层之上新增执行层，而不是重做底层会话模型。

## 测试决策

- 好的测试应验证外部行为，而不是绑定内部实现细节。测试应关注“系统对用户和调用方表现出了什么行为”，而不是“内部调用了哪个私有函数”。
- 本项目继续遵循 `TDD`，先写失败测试，再写最小实现，再做真实上游验证。
- 需要重点覆盖的模块和行为包括：
  - 会话存储层：验证会话、消息、回答快照和摘要在本机持久化后的创建、读取、更新、删除行为。
  - 会话服务层：验证新建、重命名、删除、恢复历史会话和更新时间排序行为。
  - 追问判定模块：验证其在基础指代、条号继承、法规对象继承、非追问场景下的输出行为。
  - 上下文管理模块：验证“最近 N 轮 + 更早摘要”的组装逻辑、裁剪规则和摘要失效后的降级行为。
  - 检索编排模块：验证追问场景下仍然重新检索，且不会直接把旧引文当作新依据。
  - 回答编排模块：验证前端最小展示结构的生成、修正提示逻辑、条款原文展示切换逻辑。
  - 会话管理 API：验证会话列表、创建、详情、重命名、删除的契约行为。
  - 对话执行 API：验证在新问题、追问、证据不足、建库未完成、模型失败、修正前文等场景下的响应契约。
  - 前端关键交互：验证会话列表切换、新建、重命名、删除、继续追问和历史恢复的用户流程。
- 需要延续当前代码库中已有的测试风格：
  - 服务层已有查询规范化、检索、答案生成等模块化单元测试，可作为新增应用层深模块的先例。
  - API 层已有聊天接口和依赖注入相关集成测试，可作为会话管理与消息执行接口的先例。
  - 离线流水线已有小型集成测试，可作为“知识库已构建时的端到端行为验证”先例。
- 所有新增或修改测试，除单元/预编写测试外，还必须基于真实上游产物补做一轮真实验证，验证多轮会话在真实 `data/normalized`、`data/structured`、`data/chunks`、`data/index` 上的表现。
- 真实验证应重点覆盖：
  - 重启服务后历史会话是否仍可读取；
  - 在真实索引上继续追问时是否仍能返回有效法律依据；
  - 当本轮检索依据变化时是否正确显示修正提示；
  - 长会话在真实运行中是否能通过摘要和裁剪保持可用。

## 非本期范围

- 多用户账户、权限模型、租户隔离和共享会话。
- 会话搜索、筛选、标签、收藏和导出。
- 多标签页实时同步和跨设备同步。
- 检索调试面板、候选结果打分明细、完整 prompt 展示和原始模型返回调试视图。
- 跳过检索的追问策略、直接复用旧答案的捷径方案。
- 真正的自主规划 Agent、工具调用编排、多步执行状态机和运行回放系统。
- 以云部署、任务队列或容器编排为目标的生产化部署设计。

## 补充说明

- 本 PRD 的首要目标是把当前系统从“单轮 RAG 验证面板”提升到“可持续使用的本地问答产品”，而不是追求一次性做完所有高级能力。
- `Phase 1 / MVP` 应严格聚焦于：本机单用户会话系统、会话持久化、历史恢复、基础追问、上下文管理、修正提示和简洁界面。
- `Phase 2` 可考虑会话搜索、导出、知识库更新提示、追问判定优化和更丰富的前端交互。
- `Phase 3` 若未来业务需要真正的 Agent，再在当前会话应用层之上扩展执行层。
- 下一阶段若进入实施规划，应基于本 PRD 继续拆出：
  - 会话数据模型与数据库设计；
  - 在线应用层模块职责与接口；
  - 前端页面结构与交互流；
  - 分阶段实施计划与验收命令。
