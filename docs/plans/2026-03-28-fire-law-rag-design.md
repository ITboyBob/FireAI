## 二、总体架构

系统是一个本机单体应用，但必须严格区分“离线建库”和“在线查询”。

### 2.1 离线链路

1. 从 `法律文本/` 读取原始文件
2. 标准化为干净文本
3. 解析法律结构与元数据
4. 按条切块，必要时按段落进一步拆分
5. 构建：
   - `SQLite FTS5` 关键词索引
   - 通过可替换向量存储接口暴露的向量索引，默认实现为 `FAISS`
6. 将所有生成物统一落盘到 `data/`

### 2.2 在线链路

1. 从薄网页聊天页接收用户问题
2. 规范化查询
3. 执行元数据过滤
4. 对关键词索引与向量索引执行混合检索
5. 去重、排序、裁剪证据
6. 调用 OpenAI 兼容聊天模型
7. 返回固定结构响应：
   - 结论
   - 条文依据
   - 适用范围
   - 不确定点 / 证据不足说明

### 2.3 设计约束

- 原始语料只读，不回写
- 在线请求不重建索引
- 每份生成物都必须可见、可检查
- 证据不足时必须拒答，不能靠模型补全
- 模型和索引实现可以替换，但应用侧接口必须稳定

### 3.1 目录边界

- `法律文本/`：原始输入，不能混入任何生成物
- `data/`：离线流水线可重建产物
- `var/`：仅运行时文件，如日志和临时文件
- `app/`、`scripts/`、`tests/`、`docs/`：应纳入仓库管理的项目资产

## 四、模块职责

- `CorpusIngestor`：发现并登记原始输入文件
- `Normalizer`：完成文档转换与清洗
- `StructureParser`：抽取法律层级与元数据
- `ChunkBuilder`：生成按条优先的 chunks，并保留路径
- `IndexBuilder`：离线构建关键词索引与向量索引
- `QueryNormalizer`：规范化用户查询并抽取过滤线索
- `Retriever`：执行元数据感知的混合检索
- `EvidenceAssembler`：整理证据供模型使用
- `AnswerService`：基于证据生成受约束回答
- `Web/UI Layer`：仅承担最小输入/输出展示
- `Config`：统一管理模型、路径与检索参数

## 五、配置边界

第一阶段只保留三类可替换接缝：

- `ChatClient`
  - 对接 OpenAI 兼容聊天接口
  - 配置项：`base_url`、`api_key`、`model`、`timeout`、`temperature`

- `Embedder`
  - 对接本地句向量 / 检索模型
  - 配置项：`model_name_or_path`、`device`、`batch_size`、`max_seq_length`

- `RetrieverStore`
  - 统一访问关键词索引与向量索引
  - 配置项：索引路径、`top_k`、融合权重、最低分阈值

第一阶段不引入插件系统、注册中心或泛化的 Agent 编排层。

## 六、错误处理

### 6.1 离线链路

- 文档转换失败时，按文档记失败
- 结构解析失败时，写入构建报告
- 索引构建失败时，整体步骤直接失败
- 每次构建必须产出摘要：成功数、失败数、失败原因、输出路径

### 6.2 在线链路

- 索引缺失时，返回“尚未完成建库”
- 证据不足时，返回拒答态
- 模型调用失败时，与检索失败分开暴露
- 无法绑定引文时，直接拒答

系统不得静默退化为“无检索纯大模型回答”。

### 7.1 单元测试

- 响应必须包含结论 / 引文 / 适用范围 / 不确定点
- 证据不足必须拒答
- 引文字段必须能回溯到 `document_id` 与条文路径

### 7.4 人工验收

## 八、`.gitignore` 原则

应忽略：

- Python 缓存和虚拟环境
- `.env` 及本机私密配置（保留 `.env.example`）
- `var/`
- 日志
- 本地模型缓存
- `data/` 下可重建生成物
- 编辑器与系统噪声

不应忽略：

- `法律文本/`
- 应用代码
- 脚本
- 测试
- 文档
- 项目元数据文件

若未来出现“人工维护”的 JSON 配置，不得放入 `data/` 中，而应放入受版本管理的源码或配置目录。

## 九、技术审查备注

- 当前语料规模仍然较小，引入 Neo4j、独立向量数据库服务或重框架都为时过早。
- “本地嵌入模型”不等于默认上原始 BERT，应优先句向量或检索导向模型。
- 网页界面在第一阶段只是 RAG 验证面板，不是独立产品前端。
- 可扩展性来自窄接口和清晰边界，而不是过早的插件化设计。
