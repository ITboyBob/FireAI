# todo 法律语料评估基线

**日期：** 2026-06-28  
**角色：** `reference_material`  
**用途：** 记录多格式摄取设计的当前真实样本证据，不定义长期运行规则。

## 1. 评估范围

评估对象为 `法律文本/todo/` 下除 `.DS_Store` 外的全部 14 份文件。

评估仅执行只读探针：

- 检查真实文件类型、大小和页数；
- 对 `.doc/.docx` 复用现有标准化、结构解析和切块服务；
- 对 PDF 检查文本层和逐页可提取字符量；
- 对扫描型 PDF 进行页面视觉核验；
- 不写入正式 `data/`；
- 不安装 OCR 或其他依赖；
- 不移动 `todo/` 与 `done/` 文件。

## 2. 格式分布

| 格式 | 数量 | 当前增量入口 |
| --- | ---: | --- |
| DOC | 8 | 接受 |
| DOCX | 3 | 接受 |
| PDF | 3 | 拒绝 |
| 合计 | 14 | 11 份可进入现有入口 |

3 份 PDF 中：

- 1 份具有完整文本层；
- 2 份几乎只能提取分页控制字符，属于扫描型 PDF。

## 3. 现有机制基线

现有增量机制的当前输入和成功条件：

1. 显式指定且一次只允许一份文件；
2. 后缀必须为 `.doc` 或 `.docx`；
3. 使用 `/usr/bin/textutil` 提取文本；
4. 清理空行、有限页码噪声和 HYPERLINK 域；
5. 使用正则识别编、章、节、条；
6. 生成非空 chunks；
7. 通过 append-only 冲突预检后进入 staging 和提交。

该成功条件只能证明“生成了 chunk”，不能证明正文边界、条文顺序和版本语义正确。

## 5. 已确认的差距

### 5.1 入口差距

- 3 份 PDF 全部被入口拒绝；
- 现有命令不扫描目录；
- 一次只能处理一份文件；
- 文件夹主题分类未进入生成物元数据。

### 5.2 文本提取差距

- 4 份 Word 文档的 `PAGE` 域进入最后一条正文；
- Word 表格和文本框会被线性展开；
- 文本型 PDF 存在分页硬换行；
- 扫描型 PDF 没有文字层；
- 当前没有 OCR 质量分或逐页覆盖检查。

### 5.3 法律结构差距

- 现有解析器只识别编、章、节、条；
- 最后一条之后的内容默认并入最后一条；
- 不能稳定分离发布说明、修订说明、目标正文和附件；
- 不能检测条号连续性、重复条号和条文被合并；
- 不能可靠表达法规版本依据。

### 5.4 质量门禁差距

- chunk 非空即被视为语料生成成功；
- 没有按来源类型执行专属门禁；
- 没有边界不确定状态；
- 没有批次级文件清单和遗漏检查；
- 真实 smoke 测试仍使用旧目录路径，当前会跳过。

## 6. 代表性风险

### 6.1 错误内容成功提交

页码域、印发信息和文书模板均能生成非空 chunk，因此现有成功条件无法阻止污染。

### 6.2 错误排除目标正文

`河北省消防设施管理规定.docx` 的目标法规位于带有“附件2”字样的复合修订材料之后。若以“附件”作为无条件截断词，会删除真正需要的法规正文。

### 6.3 扫描件静默漏条

OCR 对中文数字条号的误识别可能使整条法规无法被结构解析器发现。只检查最终文本非空不能发现这种遗漏。

### 6.4 append-only 放大修复成本

受污染文档提交后，同一 `document_id` 会被正式产物和索引冲突门禁阻止再次导入。上游质量门禁必须先于正式提交。

## 7. 评估结论

当前机制不需要推翻，其 staging、冲突预检、索引追加和回滚能力应继续保留。

下一阶段的主要建设对象是 append-only 提交之前的四层能力：

1. 全量发现与双轴分类；
2. 多提取器路由；
3. 目标正文边界和统一中间格式；
4. 类型专属质量门禁与批次状态。
