# 文档索引

本目录按 Harness Engineering / Context Engineering 的“稳定上下文、计划、状态隔离”原则组织。

## 文档分层

- [产品需求文档（PRD）](./plans/2026-04-11-fire-qa-system-2.0-prd.md)
  - 当前唯一产品标准。
  - 记录经确认的产品问题、目标用户、功能范围、用户故事、产品决策、测试决策与非本期范围。
  - 用于回答“为什么做、面向谁、做哪些能力、不做哪些能力、怎样才算产品验收通过”。

- [README 技术标准入口](../README.md)
  - 当前技术标准入口。
  - 记录技术架构、目录边界、运行命令、建库规则、证据约束、错误处理、测试要求和前端工程组织建议。
  - 旧设计与 README 存在技术口径冲突时，以 README 为准。

- [NDJSON 状态流设计](./plans/2026-04-23-fire-qa-ndjson-status-stream-design.md)
  - 记录“后端 NDJSON 状态流，最终可信结果由前端逐字呈现”的专项设计。
  - 覆盖 `/api/conversations/{conversation_id}/messages/stream`、事件协议、服务层编排、前端状态机、错误恢复、Playwright E2E 口径和验收边界。
  - 当任务涉及消息状态流、NDJSON 解析、typewriter、流式错误恢复或兼容一次性消息接口时读取。

- [一期 RAG 历史设计资料](./plans/2026-03-28-fire-law-rag-design.md)
  - 记录一期消防法律 RAG 的历史目标、范围、架构、目录结构、模块职责、约束与测试策略。
  - 不再作为当前产品或技术标准，只在追溯一期历史背景、理解旧实施来源时读取。
  - 旧设计与 2.0 PRD 冲突时，产品口径以 PRD 为准；旧设计与 README 冲突时，技术口径以 README 为准。

- [实施计划](./plans/2026-03-28-fire-law-rag-implementation.md)
  - 一期 RAG 历史实施计划。
  - 保留任务拆分、步骤、验收方式与执行约束，用于追溯历史实现来源。
  - 不记录滚动执行状态。

- [实施计划（消防问答系统 2.0）](./plans/2026-04-11-fire-qa-system-2.0-implementation.md)
  - 记录 2.0 会话层、多轮上下文、会话 API、前端双栏界面和 NDJSON 状态流专项的逐任务实施步骤。
  - 可直接作为当前工作区的批次执行计划使用。

- [架构决策记录（ADR）](./adr/2026-03-28-normalization-and-chunking-refactor.md)
  - 记录关键取舍：为什么选这个方案、拒绝了什么替代方案、门禁为什么存在。
  - 不承担滚动状态，也不代替实施步骤。

- [技术债记录](./debts/2026-03-29-chunk-builder-enum-red-test-debt.md)
  - 记录已经识别、已知存在、但当前主线选择暂缓处理的工程债务。
  - 用于解释“为什么当前不修、临时如何放行、未来怎样解除”。

- [项目状态](./status.md)
  - 本仓库唯一的执行状态文档。
  - 只记录需要沉淀的任务进展、运行环境、验证结果和当前阻塞点。
  - 不要求纯文档小改、只读分析或无状态影响的简单任务自动更新。

## 使用规则

- 需要理解“这期产品到底要解决什么问题、做哪些能力、不做哪些能力”时，读 PRD；PRD 是唯一产品标准。
- 需要理解当前技术架构、目录边界、运行方式、测试要求、证据约束和工程规则时，读 README；README 是当前技术标准入口。
- 需要理解“后端 NDJSON 状态流、最终可信结果前端逐字呈现、事件协议、错误恢复或流式状态验收”时，读 NDJSON 状态流设计。
- 需要追溯一期 RAG 为什么这样设计时，读一期 RAG 历史设计资料；不要把旧设计直接当作当前标准。
- 需要理解“当前消防问答系统 2.0 主线做到哪一层、下一步按什么任务继续推进”时，优先看 2.0 实施计划与项目状态，而不是回到旧的单轮实施计划。
- 需要理解“为什么选这个重构方案、为什么任务被门禁拦住、为什么不能采用其他方案”时，读 ADR。
- 需要理解“为什么某条已知红测当前不修、为什么它不应继续阻塞主线放行”时，读技术债记录。
- 需要追溯旧单轮 RAG 主线时，看旧实施计划；需要按 2.0 会话系统主线推进实现时，看 2.0 实施计划。
- 需要确认“做到哪一步、在哪个环境验证过、当前卡在哪里”时，只看项目状态文档。

## 新会话读取顺序

本节用于给人和代理解释“为什么这样读”，真正具有仓库级约束力的规则以根目录 `AGENTS.md` 为准。

1. 先读本文件，理解文档系统的分层和入口。
2. 再读 [项目状态](./status.md)，确认当前执行状态。
3. 若任务涉及产品目标、功能范围、用户故事、本期边界或产品验收，先读 [产品需求文档（PRD）](./plans/2026-04-11-fire-qa-system-2.0-prd.md)。
4. 若任务涉及技术架构、目录结构、运行命令、建库链路、证据约束、错误处理、测试策略或前端工程组织，先读 [README](../README.md)。
5. 若任务涉及 NDJSON 状态流、`/messages/stream`、前端 buffer 解析、typewriter、流式错误恢复或 Playwright E2E，读 [NDJSON 状态流设计](./plans/2026-04-23-fire-qa-ndjson-status-stream-design.md)。
6. 只有在需要追溯一期 RAG 历史背景、旧实现来源或旧计划上下文时，才读 [一期 RAG 历史设计资料](./plans/2026-03-28-fire-law-rag-design.md) 和 [一期 RAG 历史实施计划](./plans/2026-03-28-fire-law-rag-implementation.md)。
7. 若任务涉及方案取舍、任务门禁、重构原因，再读 [架构决策记录（ADR）](./adr/2026-03-28-normalization-and-chunking-refactor.md)。
8. 若任务涉及已知技术债、临时放行策略或“为什么一条红测当前不算主线阻塞”，再读 [技术债记录](./debts/2026-03-29-chunk-builder-enum-red-test-debt.md)。
9. 若任务涉及继续实现或验收，再读对应实施计划；消防问答系统 2.0 主线见 [fire-qa-system-2.0-implementation](./plans/2026-04-11-fire-qa-system-2.0-implementation.md)，当前重构门禁见 [normalization-and-chunking-refactor](./plans/2026-03-28-normalization-and-chunking-refactor.md)。

## 读取原则

- 只按任务需要加载文档，避免把所有文档一次性塞进上下文。
- `docs/status.md` 是唯一滚动状态源，不得从设计文档和实施计划中推测最新进度；但它按需更新，不承担逐任务流水账职责。
- PRD 回答“为什么做这件事、本期做什么、不做什么、怎样才算满足产品需求”。
- README 回答“当前技术上怎样组织、怎样运行、怎样建库、怎样测试、哪些工程约束必须遵守”。
- NDJSON 状态流设计回答“消息状态流如何传输、事件格式是什么、前端如何解析和逐字呈现、错误如何恢复、E2E 怎样避免 flaky”。
- 一期 RAG 历史设计资料回答“一期当时为什么这样设计”，不回答当前产品或技术标准。
- ADR 回答“为什么选这个方案”，实施计划回答“接下来怎么做”，状态文档回答“现在做到哪里”。
- 技术债记录回答“哪些问题已知存在但当前选择不修、为什么不修、怎样临时放行、未来怎样解除”。
